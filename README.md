# rhythm-godot

A Dance of Fire and Ice(얼불춤) 스타일의 **원버튼 리듬게임**. Godot 4.7 / GDScript.

두 행성이 꺾인 타일 경로를 번갈아 공전한다. 버튼은 스페이스 하나뿐이고,
낙하 노트가 없다 — **타일의 각도가 곧 대기 박자 수**라서 눈이 아니라 귀와 손으로 푸는 게임이다.

설계 배경과 결정 근거: `~/.gstack/projects/rhythm-godot/kyb-ontact-main-design-*.md`

---

## 이 게임의 심장

```
공전 각속도가 박자당 180도로 고정이면, 타일 사이 상대각이 곧 대기 시간이다.

         prev+180 (공전 시작)
              \
               \   sweep
                \ ,-'`
        [pivot]  o------> cur (다음 타일 방향)

    sweep = fposmod(cur - (prev + 180), 360)     # 0 이면 360
    beats = sweep / 180

    직선 (cur==prev)     -> sweep 180 -> 1.0박
    U턴  (cur==prev+180) -> sweep 360 -> 2.0박
    90도 꺾임            -> sweep 270 -> 1.5박
```

따라서 **노트 타임라인이라는 자료구조가 아예 필요 없다.** 각도 배열 하나가
렌더와 타이밍을 동시에 생성한다. 두 개의 진실 소스가 없으므로 둘이 어긋날 수 있는
버그 표면 자체가 사라진다. (대부분의 클론이 여기서 어긋난다.)

### 이 공식은 실측 검증됐다

```bash
python3 tools/verify_formula.py <실제 .adofai 파일들>
```

- ADOFAI 기본 레벨(직선 10타일 @ bpm 100) → **정확히 1.0박 / 600ms 간격**
- 실제 채보 3,155타일 → 최빈값이 정확히 1.0(34%), 모든 값이 1/12 격자, 쓰레기 값 0
- 반증 대조군: `+180` 을 빼면 직선이 **2박**이 되어 즉시 탈락

검증 중 알게 된 것 3가지:

1. **`.adofai` 는 유효한 JSON 이 아니다.** 실제 파일에서 위반 3종 발견 —
   이중 콤마(`"difficulty": 1, ,`), 트레일링 콤마, 섹션 간 콤마 누락.
   `tools/verify_formula.py:load_adofai()` 가 이걸 감안해 읽는다.
2. **CCW/CW 규약은 이 증거로 결정되지 않는다.** 두 변형이 직선·U턴에서 같고
   좌/우 회전에서만 갈린다(1.5 ↔ 0.5). 우리가 채보를 직접 짜므로 무관하지만,
   실제 `.adofai` 를 로드하려면 정해야 한다.
3. **실제 채보는 이 프로젝트가 모델링하는 것보다 훨씬 복잡하다.**
   샘플 채보는 SetSpeed 132개(bpm 128→512)에 Twirl 이 타일의 25%.
   → "직접 짠 채보만 쓴다"는 결정이 옳았다는 증거다.

## 구조

```
AudioClock.tscn                  autoload — 씬으로 등록
└── AudioStreamPlayer            클럭이 자기 재생 노드를 소유한다

Main.tscn                        씬 리로드로 재시작해도 안전
├── World
│   ├── Camera2D                 위치도 오디오 클럭에서 파생
│   ├── Path (Line2D)            각도 배열을 그대로 그린 경로
│   ├── PlanetPair               set_orbit_progress(u) — Tween 없음
│   │   ├── PlanetA / PlanetB
│   └── JudgmentPopup
├── Judge                        판정창 3개가 @export
└── UI
    ├── CalibrationPanel         오프셋 슬라이더 ±150ms
    └── DebugOverlay             표본·평균·표준편차·clamp_hits·output_latency
```

| 스크립트 | 역할 |
|---|---|
| `ChartRuntime.gd` | 각도→박자·좌표. **순수 static 함수만.** 단위 테스트 대상은 여기뿐 |
| `Chart.gd` | Resource. 채보의 단일 진실 소스 |
| `AudioClock.gd` | 오디오 클럭 + 재생 소유. autoload |
| `Judge.gd` | ms 판정만. 렌더도 상태 전진도 모름 |
| `Main.gd` | 배선 + TileCursor 상태 + 감시자/입력자 |

### 지키는 규칙 3개

**1. 판정은 오디오 클럭 ms 차이로만 한다.** 좌표 겹침도 프레임 카운트도 안 쓴다.

```gdscript
var ms := (get_playback_position() + AudioServer.get_time_since_last_mix()
           - AudioServer.get_output_latency()) * 1000.0
_last_ms = maxf(ms, _last_ms)   # 스레드 지터로 역행할 수 있다(공식 문서 경고)
```

`get_playback_position()` 만 쓰면 오디오 스레드가 다음 청크를 믹싱할 때까지 같은 값을
돌려주므로 클럭이 믹스 버퍼만큼의 계단으로 뚝뚝 뛴다. 그 계단폭이 그대로 판정 잡음이 된다.

**2. `now_ms()` 는 `_input()` 과 `_process()` 각각에서 그 자리에서 부른다. 캐시 금지.**
`_process` 에 캐시한 값을 `_input` 에서 쓰면 최대 1프레임(60fps 에서 16.7ms)이
판정 오차로 그냥 들어간다.

**3. 시간축은 하나뿐이다. `Tween` 을 쓰지 않는다.**
Tween 은 프레임 루프가 굴리는 벽시계라 오디오 클럭과 별개의 두 번째 시간축이 된다.
가장 흔한 증상은 크래시가 아니라 **"행성은 아직 도착 안 했는데 판정은 Perfect"** —
눈과 손이 불일치하는, 진단이 가장 어려운 종류다.
공전각도 카메라 위치도 전부 `now_ms()` 에서 파생시킨다.

같은 이유로 **캘리브레이션 오프셋을 클럭 안에서 빼지 않는다.** 클럭 안에서 빼면
슬라이더를 미는 순간 ① `clamp_hits` 가 올라가고(하드 게이트의 거짓양성)
② `maxf` 가 이전 값을 붙잡아 클럭이 오프셋만큼 얼어붙는다. 오프셋은 판정 시점에 뺀다.

## 실행

```bash
# 곡(메트로놈 클릭) 생성 — BPM 이 샘플 단위로 정확해야 한다
python3 tools/make_click.py 120 60

# 채보 생성 — 각도를 손으로 안 쓴다. 박자 패턴에서 역산한다
python3 tools/make_charts.py

# 단위 테스트 (의존성 0)
godot --headless --script res://tests/run_tests.gd

# 실행
godot -e     # 에디터
godot        # 바로 실행
```

**조작:** `스페이스` 판정 · `R` 재시작

### 곡을 왜 만들어 쓰나

음악은 BPM 이 정확히 알려져 있지 않거나 변속이 있거나 그루브가 있다. 판정이 어긋났을 때
원인이 내 코드인지 곡인지 구분이 안 된다. 클릭은 샘플 단위로 정확하다 —
실측 결과 간격 오차 최대 0.042ms, 60초 누적 드리프트 +0.08ms.

WAV 를 쓰는 이유: 손실 압축은 어택 트랜지언트를 뭉갠다. 디코더 지연 편차도 없다.
용량이 크므로 gitignore 하고 생성기만 커밋한다.

### 2단계 계측 비교표 (Godot 설치 후 채운다)

| 설정 / 변형 | 표준편차 |
|---|---|
| `agile_event_flushing` OFF (기본) | ? ms |
| `agile_event_flushing` ON | ? ms |
| `vsync_mode` ON / OFF | ? ms |
| `output_latency` 15ms / 낮춤 | ? ms |
| 3항 공식 (`pos + since_mix - latency`) | ? ms |
| 1항 (`pos` 만) | ? ms |

마지막 두 행은 크로스모델 논쟁을 숫자로 끝내려고 넣었다. 독립 리뷰어가
"3항은 과잉"이라고 했고, 반박은 "그 항은 변덕에 대한 보험이 아니라 상시 존재하는
계단 현상을 메우는 항"이다. 하네스가 어차피 생기므로 재서 끝낸다.

### 성공 기준

1. 30초 이상 완주 + **연속 3회 재시작**해도 판정 동일 (`_last_ms` 리셋 검증)
2. 오프셋 슬라이더 ±150ms, 다음 판정부터 즉시 반영
3. **판정 오차 표준편차 < 15ms** — 같은 구간 10회 반복, 모든 `delta_i` 를 한 표본으로
   - 미달 시: 즉시 실패로 보지 말고 오디오 백엔드·버퍼·`output_latency` 실측값부터 로그.
     백엔드를 바꿔도 안 줄면 그건 코드 결함이 아니라 기계의 바닥이다.
     **코드 결함과 기계 바닥을 구분하는 게 목적이지 15라는 숫자가 목적이 아니다.**
4. `clamp_hits == 0` (하드 게이트). **슬라이더를 아무리 밀어도 안 올라가야 한다** —
   올라간다면 오프셋이 아직 `now_ms()` 안에 남아 있다는 신호
5. 판정 피드백이 입력 후 33ms 이내
