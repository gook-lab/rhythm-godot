# rhythm-godot

A Dance of Fire and Ice(얼불춤) 스타일의 **원버튼 리듬게임**. Godot 4.7 / GDScript.

두 행성이 꺾인 타일 경로를 번갈아 공전한다. 버튼은 스페이스 하나뿐이고,
낙하 노트가 없다 — **타일의 각도가 곧 대기 박자 수**라서 눈이 아니라 귀와 손으로 푸는 게임이다.

설계 배경과 결정 근거: `~/.gstack/projects/rhythm-godot/kyb-ontact-main-design-*.md`

---

## 이 게임의 심장

```
공전 각속도가 박자당 180도로 고정이면, 타일 사이 상대각이 곧 대기 시간이다.

         prev+180 (공전 시작)
              \
               \   sweep
                \ ,-'`
        [pivot]  o------> cur (다음 타일 방향)

    sweep = fposmod(cur - (prev + 180), 360)     # 0 이면 360
    beats = sweep / 180

    직선 (cur==prev)     -> sweep 180 -> 1.0박
    U턴  (cur==prev+180) -> sweep 360 -> 2.0박
    90도 꺾임            -> sweep 270 -> 1.5박
```

따라서 **노트 타임라인이라는 자료구조가 아예 필요 없다.** 각도 배열 하나가
렌더와 타이밍을 동시에 생성한다. 두 개의 진실 소스가 없으므로 둘이 어긋날 수 있는
버그 표면 자체가 사라진다. (대부분의 클론이 여기서 어긋난다.)

### 이 공식은 실측 검증됐다

```bash
python3 tools/verify_formula.py <실제 .adofai 파일들>
```

- ADOFAI 기본 레벨(직선 10타일 @ bpm 100) → **정확히 1.0박 / 600ms 간격**
- 실제 채보 3,155타일 → 최빈값이 정확히 1.0(34%), 모든 값이 1/12 격자, 쓰레기 값 0
- 반증 대조군: `+180` 을 빼면 직선이 **2박**이 되어 즉시 탈락

검증 중 알게 된 것 3가지:

1. **`.adofai` 는 유효한 JSON 이 아니다.** 실제 파일에서 위반 3종 발견 —
   이중 콤마(`"difficulty": 1, ,`), 트레일링 콤마, 섹션 간 콤마 누락.
   `tools/verify_formula.py:load_adofai()` 가 이걸 감안해 읽는다.
2. **CCW/CW 규약은 이 증거로 결정되지 않는다.** 두 변형이 직선·U턴에서 같고
   좌/우 회전에서만 갈린다(1.5 ↔ 0.5). 우리가 채보를 직접 짜므로 무관하지만,
   실제 `.adofai` 를 로드하려면 정해야 한다.
3. **실제 채보는 이 프로젝트가 모델링하는 것보다 훨씬 복잡하다.**
   샘플 채보는 SetSpeed 132개(bpm 128→512)에 Twirl 이 타일의 25%.
   → "직접 짠 채보만 쓴다"는 결정이 옳았다는 증거다.

## 구조

```

└── AudioStreamPlayer            클럭이 자기 재생 노드를 소유한다

Main.tscn                        씬 리로드로 재시작해도 안전
├── World
│   ├── Camera2D                 위치도 오디오 클럭에서 파생
│   ├── Path (Line2D)            각도 배열을 그대로 그린 경로
│   ├── PlanetPair               set_orbit_progress(u) — Tween 없음
│   │   ├── PlanetA / PlanetB
│   └── JudgmentPopup
├── Judge                        판정창 3개가 @export
└── UI
    ├── CalibrationPanel         오프셋 슬라이더 ±150ms
    └── DebugOverlay             표본·평균·표준편차·clamp_hits·output_latency
```

| 스크립트 | 역할 |
|---|---|
| `ChartRuntime.gd` | 각도→박자·좌표. **순수 static 함수만.** 단위 테스트 대상은 여기뿐 |
| `Chart.gd` | Resource. 채보의 단일 진실 소스 |
| `AudioClock.gd` | 오디오 클럭 + 재생 소유. autoload |
| `Judge.gd` | ms 판정만. 렌더도 상태 전진도 모름 |
| `Main.gd` | 배선 + TileCursor 상태 + 감시자/입력자 |

### 지키는 규칙 8개

**1. 판정은 오디오 클럭 ms 차이로만 한다.** 좌표 겹침도 프레임 카운트도 안 쓴다.

```gdscript
var ms := (get_playback_position() + AudioServer.get_time_since_last_mix()
           - AudioServer.get_output_latency()) * 1000.0
_last_ms = maxf(ms, _last_ms)   # 스레드 지터로 역행할 수 있다(공식 문서 경고)
```

`get_playback_position()` 만 쓰면 오디오 스레드가 다음 청크를 믹싱할 때까지 같은 값을
돌려주므로 클럭이 믹스 버퍼만큼의 계단으로 뚝뚝 뛴다. 그 계단폭이 그대로 판정 잡음이 된다.

**2. `now_ms()` 는 `_input()` 과 `_process()` 각각에서 그 자리에서 부른다. 캐시 금지.**
`_process` 에 캐시한 값을 `_input` 에서 쓰면 최대 1프레임(60fps 에서 16.7ms)이
판정 오차로 그냥 들어간다.

**3. 시간축은 하나뿐이다. `Tween` 을 쓰지 않는다.**
Tween 은 프레임 루프가 굴리는 벽시계라 오디오 클럭과 별개의 두 번째 시간축이 된다.
가장 흔한 증상은 크래시가 아니라 **"행성은 아직 도착 안 했는데 판정은 Perfect"** —
눈과 손이 불일치하는, 진단이 가장 어려운 종류다.
공전각도 카메라 위치도 전부 `now_ms()` 에서 파생시킨다.

같은 이유로 **캘리브레이션 오프셋을 클럭 안에서 빼지 않는다.** 클럭 안에서 빼면
슬라이더를 미는 순간 ① `clamp_hits` 가 올라가고(하드 게이트의 거짓양성)
② `maxf` 가 이전 값을 붙잡아 클럭이 오프셋만큼 얼어붙는다. 오프셋은 판정 시점에 뺀다.

**4. 렌더 커서와 판정 커서는 별개다. 둘 다 `now_ms()` 에서 파생되지만 전진 조건이 다르다.**

| 커서 | 전진 조건 | 쓰는 곳 |
|---|---|---|
| `_idx` (판정) | 입력이 오거나 `hit_time + miss_ms` 경과 | 판정, 판정창 |
| `_vis` (렌더) | `t >= hit_time` — 그냥 시간이 지나면 | 공전각, 카메라, 팝업 위치 |

묶어두면 **행성이 매 타일 `miss_ms` 만큼 얼어붙는다.** 감시자는 늦은 입력을 받아주려고
기한까지 기다려야 하는데, 렌더가 그걸 따라가면 u=1.0 에 붙어서 멈춘다.

실측: 렌더를 판정 커서에 묶으면 전체 프레임의 **25.8%** 가 정지 상태다
(0.5박@120bpm 구간은 250ms 중 110ms = 44%). 분리하면 **0.7%** 로 떨어진다.
`tests/SmokeRunner.gd` 가 이 비율을 재서 8% 를 넘으면 실패시킨다.

**5. 카메라는 순간 위치가 아니라 '주변 타일의 평균'을 본다.**

행성이든 축이든 중점이든, **순간 위치를 쫓으면 경로의 지그재그를 그대로 따라가서
위아래로 튄다.** demo 채보만 해도 90도 4연속(사각형)이 두 번, U턴이 세 번 있어서
길이 진짜로 되돌아온다. 알고리즘 문제가 아니라 경로 문제다.

그래서 앞뒤 ±2 타일의 평균을 본다(`Main.CAMERA_WINDOW`). 사각형 구간이면
사각형 중심에 머문다. 창이 대칭이라 앞으로 올 타일도 반영된다(선행 시야).
타일 사이는 `u` 로 연속 보간해서 타깃이 계단으로 뛰지 않게 한다.

실측 — 경로 낭비 배수(실제 이동거리 / 순 이동거리, 1 이면 곧게 따라감):

| 카메라 타깃 | 프레임이동 최대 | 낭비배수 | 행성까지 최대 |
|---|---|---|---|
| 타일 사이 직선 lerp | 29.35 px | 5.86x | 147 px |
| 두 행성 중점 | 5.11 px | **8.17x** | 48 px |
| 축(현재 타일)만 | 96.00 px | 6.50x | 96 px |
| **주변 타일 평균 ±2** | **3.09 px** | **2.65x** | 194 px |

중점은 위치 연속성은 최고였지만(축 주위 반지름 48px 원) 오히려 가장 많이 흔들렸다.
두 지표를 같이 안 보면 한쪽을 고치면서 다른 쪽을 망친다.

창 크기 트레이드오프: ±1 은 4.07x/162px · ±2 는 3.32x/194px · ±3 은 3.10x/242px.
크게 잡을수록 차분하지만 행성이 화면 중심에서 멀어진다.

흔들림(미스 연출)은 `position` 이 아니라 `offset` 으로 준다 — `position` 에 실으면
`position_smoothing` 이 뭉개서 '흔들림'이 아니라 '느린 표류'가 된다.

**6. 미스마다 화면을 흔들지 않는다. 콤보가 실제로 끊길 때만 짧게 흔든다.**

리듬게임에서 미스는 흔한 일이다. 흔들림이 타일 간격(250~500ms)보다 길면
사실상 상시 진동이 된다. 실측: 14px/233ms 로 매 미스마다 흔들었더니
**전체 프레임의 47.3%** 가 흔들리고, 화면에 보이는 경로 낭비가
2.65x -> **18.01x** 로 뛰었다.

그리고 `randf()` 로 매 프레임 방향을 바꾸면 안 된다. 144fps 면 초당 144번
방향이 바뀌어서 '충격'이 아니라 '떨림'으로 읽히고, fps 에 따라 체감도 달라진다.
고정 주파수(22Hz) 감쇠 진동을 쓴다.

| | 흔들리는 프레임 | 보이는 경로 낭비 |
|---|---|---|
| 미스마다 14px/233ms · 매 프레임 랜덤 | 47.3 % | 18.01x |
| **콤보 3+ 끊길 때만 7px · 22Hz** | **4.5 %** | **3.06x** |

> **계측 함정:** 흔들림을 `offset` 으로 옮긴 뒤에도 지표는 `position` 만 재고 있었다.
> 그래서 "카메라 낭비 2.65x, 통과"라고 보고했는데 실제로 보이는 값은 18.01x 였다.
> 지금은 **연속성은 `position`, 흔들림은 `position + offset`** 으로 나눠 잰다.
> 섞으면 정당한 흔들림이 연속성 실패로 오인된다.

**7. 채보에는 카운트인이 있어야 한다 (기본 4박).**

음악적으로도 필요하지만 기술적으로도 필요하다. `AudioClock` 워밍업(100ms) 동안
렌더가 멈춰 있는데, 첫 타일이 0ms 에 있으면 warm 되는 순간 그만큼을 한 번에
건너뛰어 카메라가 32px 튄다. `tools/make_charts.py:LEAD_IN_BEATS`.

**8. 인덱스는 `angles[i-2]`(들어온 방향)와 `angles[i-1]`(나갈 방향)이다. `angles[i]` 가 아니다.**

타일 `i` 로 가는 공전은 축이 타일 `i-1` 이고, 도는 행성이 타일 `i-2` 에서 출발해
타일 `i` 에 착지한다. 그러니 스윕을 정하는 건 `angles[i-2]` 와 `angles[i-1]` 이다.
`angles[i]` 는 타일 `i` 에서 그 다음으로 나갈 방향이라 한 칸 미래다.

첫 구현이 여기서 한 칸 밀려 있었다. **직선 구간에선 착지 오차가 정확히 0 이라
전혀 안 보이고**, 꺾이는 데서만 드러난다:

| 경로 | 밀렸을 때 착지 오차 | 고친 뒤 |
|---|---|---|
| 직선 | 0.00 px | 0.00 px |
| 90도 계단 | 135.76 px | 0.00 px |
| 사각형(90도 4연속) | 135.76 px | 0.00 px |
| U턴 | 192.00 px | 0.00 px |

타일 간격이 96px 이니 최대 두 칸을 벗어난 채 내렸다가 튄 것이다.
`tests/run_tests.gd:t_landing()` 이 여섯 가지 경로 모양에 대해 좌표로 잠근다.
`tools/make_charts.py` 도 채보를 만들 때마다 같은 불변식을 잰다.

## 실행

```bash
# 곡(메트로놈 클릭) 생성 — BPM 이 샘플 단위로 정확해야 한다
python3 tools/make_click.py 120 60

# 채보 생성 — 각도를 손으로 안 쓴다. 박자 패턴에서 역산한다
python3 tools/make_charts.py

# 단위 테스트 (의존성 0) — 85종
godot --headless --script res://tests/run_tests.gd

# 통합 스모크 (전곡 완주 · 감시자 · 곡종료 · 클럭 역행 · 카메라 · 흔들림)
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn

# 자동 플레이 — 판정 체인 전체 검증 (랭크 P / 100% / σ 2.1ms 가 나와야 한다)
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn -- --autoplay

# 일부러 놓치기 — 콤보 끊김과 흔들림 발동 검증
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn -- --autoplay --miss-every=5

# 조작 표면 — 등급 매핑 · echo 필터 · R 재시작 · 워밍업/종료 후 입력
godot --headless --audio-driver CoreAudio res://tests/InputScene.tscn

# 오디오 클럭 실측 (드리프트·지터·3항vs1항)
godot --headless --audio-driver CoreAudio --script res://tests/probe_clock.gd

# 실행
godot -e     # 에디터
godot        # 바로 실행
```

**조작:** `스페이스` 판정 · `R` 재시작

### 곡을 왜 만들어 쓰나

음악은 BPM 이 정확히 알려져 있지 않거나 변속이 있거나 그루브가 있다. 판정이 어긋났을 때
원인이 내 코드인지 곡인지 구분이 안 된다. 클릭은 샘플 단위로 정확하다 —
실측 결과 간격 오차 최대 0.042ms, 60초 누적 드리프트 +0.08ms.

WAV 를 쓰는 이유: 손실 압축은 어택 트랜지언트를 뭉갠다. 디코더 지연 편차도 없다.
용량이 크므로 gitignore 하고 생성기만 커밋한다.

| 역행 횟수 (3초) | 7 | **0** |

**오디오 클럭이 먹는 몫은 0.78ms다.** 성공기준 3의 예산이 15ms이므로
나머지 14ms 이상이 입력 경로와 사람 손 몫으로 남는다.
이 프로젝트가 가장 걱정하던 리스크(오디오 클럭이 손맛을 죽인다)는 해소됐다.

**헤드리스 기본값(Dummy)의 −4% 드리프트에 주의.** 드리프트는 캘리브레이션으로
못 잡는다(시간이 갈수록 벌어지므로). 자동 타이밍 측정을 돌릴 거면 반드시
`--audio-driver CoreAudio` 를 붙여야 한다. 붙이면 CI 에서도 잴 수 있다.

#### 3항 vs 1항 — 크로스모델 논쟁 종결

| 공식 | 지터 |
|---|---|
| **3항** `pos + since_mix - latency` | **0.78 ms** |
| 1항 `pos` 만 | 3.44 ms |

독립 리뷰어가 "3항은 과잉이니 `get_playback_position()` 만으로 시작하라"고 했고,
반박은 "그 항은 변덕에 대한 보험이 아니라 상시 존재하는 계단 현상을 메우는 항"이었다.
**실측 결과 3항이 지터를 2.66ms 줄인다** — 전체 15ms 예산의 18%다. 조기 최적화가 아니다.

#### 아직 안 잰 것

| 설정 | 표준편차 |
|---|---|
| `agile_event_flushing` OFF (기본) / ON | ? ms |
| `vsync_mode` ON / OFF | ? ms |
| `output_latency` 15ms / 낮춤 | ? ms |

입력 경로 설정은 **사람이 실제로 키를 쳐야** 잴 수 있어서 프로브로는 안 된다.
게임을 띄워 놓고 디버그 오버레이의 표준편차를 보면서 켜고 꺼야 한다.

### 성공 기준

1. 30초 이상 완주 + **연속 3회 재시작**해도 판정 동일 (`_last_ms` 리셋 검증)
2. 오프셋 슬라이더 ±150ms, 다음 판정부터 즉시 반영
3. **판정 오차 표준편차 < 15ms** — 같은 구간 10회 반복, 모든 `delta_i` 를 한 표본으로
   - 미달 시: 즉시 실패로 보지 말고 오디오 백엔드·버퍼·`output_latency` 실측값부터 로그.
     백엔드를 바꿔도 안 줄면 그건 코드 결함이 아니라 기계의 바닥이다.
     **코드 결함과 기계 바닥을 구분하는 게 목적이지 15라는 숫자가 목적이 아니다.**
4. **클럭 역행의 *크기*가 한 믹스 청크(~6ms)를 넘지 않을 것.** 횟수가 아니다.
   - 실측: 20초 재생에 역행 20회, 최대 5.7ms. **0 이 아닌 게 정상이다.**
     `get_playback_position()` 과 `get_time_since_last_mix()` 가 서로 독립적으로
     갱신돼서, 믹싱 직후에 샘플링하면 옛 `pos` 에 리셋된 `since_mix` 가 붙는다.
     구조적으로 일어나는 일이고 단조 클램프가 바로 그걸 막으라고 있다.
   - `get_output_latency()` 를 시작 시점에 고정해봐도 크기가 그대로였다 —
     latency 지터가 원인이 아니다.
   - **슬라이더를 아무리 밀어도 역행이 늘면 안 된다** — 늘면 오프셋이 아직
     `now_ms()` 안에 남아 있다는 신호다.
5. 판정 피드백이 입력 후 33ms 이내

## 판정과 점수

### 7등급 (얼불춤 체계)

```
TooEarly · VeryEarly · EarlyPerfect · Perfect · LatePerfect · VeryLate · TooLate
```

Perfect 가 3종(E/일반/L)이고 **일반 Perfect 만 정확도 만점**이다. 이게 있어야
"다 맞혔지만 살짝씩 어긋난" 플레이와 "정확한" 플레이가 구분되고, 손맛을
개선했는지 알 수 있다. 랭크는 `P / SS / S / A / B / C / D / F` —
P 는 전부 일반 Perfect 일 때만 나온다.

### 판정창은 BPM 에 따라 좁아진다

고정 ±110ms 로 두면 **인접 타일 간격이 220ms 밑으로 내려가는 순간 판정창이 겹쳐서
한 번 누른 입력이 두 타일 모두에 유효해진다.**

| 박자 | bpm | 간격 | 고정창(±110) 여유 |
|---|---|---|---|
| 0.5박 | 120 | 250ms | +30ms (아슬아슬) |
| 0.5박 | 140 | 214ms | **−6ms 겹침** |
| 1/6박 | 340 | 29ms | **−191ms 붕괴** |

그래서 판정 사다리 전체를 **이웃 타일까지 거리의 절반**으로 캡한다
(`Judge.set_gaps()`). 겹침이 구조적으로 불가능해지고, 등급 간 비율은 보존된다.
얼불춤도 같은 이유로 "빠를수록 엄격"하게 만든다.

`tests/run_tests.gd:t_judge_windows()` 가 250·214·125·29·8ms 간격에서
창 폭이 간격을 절대 못 넘는지 잠근다.

### HUD

- **TimingScale 바** — 가운데가 정확, 왼쪽이 빠름. 최근 40개 입력이 눈금으로 찍히고
  파란 삼각형이 평균이다. **연출이자 계측 도구다**: 눈금이 한쪽으로 쏠렸으면
  오프셋 문제(슬라이더로 고쳐짐), 가운데를 중심으로 넓게 퍼졌으면 산포 문제(안 고쳐짐).
  판정창이 좁아지면 바 축척도 같이 확대돼서 눈금이 뭉치지 않는다.
- **체감 BPM** = 타일 BPM ÷ 현재 홉 박자. 1/6박 홉을 340bpm 으로 밟으면 2040 이다.
  판정창이 왜 좁아져야 하는지를 화면에서 바로 보여주는 숫자다.
- 랭크·정확도·콤보 · 음악 시간 · 역행 횟수와 최대 크기 · output_latency · fps

### 연출

네온 글로우(HDR 2D + `WorldEnvironment` glow — 색을 1.0 넘게 주면 그 부분만 블룸),
판정 등급별 행성 색 플래시(2프레임), 미스 시 화면 흔들림.
**흔들림만 프레임 시간으로 감쇠한다** — 오디오 클럭과 무관한 순수 연출이라서다.
그 외 모든 시각 요소(공전각·카메라)는 여전히 `now_ms()` 에서 파생된다.

## 테스트 제약

**`--script` 모드에선 autoload 가 등록되지 않는다.** `AudioClock` 식별자를 못 찾아서
`Main.gd` 자체가 컴파일에 실패한다. 그래서 `Main` 을 태우는 통합 테스트는
`--script` 가 아니라 **씬**(`tests/SmokeScene.tscn`)으로 만들어 정상 실행 경로에 태운다.
순수 함수만 보는 `run_tests.gd` 는 `class_name` 글로벌만 쓰므로 `--script` 로 된다.

### 잔상 트레일

두 행성이 지나간 자리를 22프레임 남긴다. 오래된 쪽이 얇고 투명해진다
(`PlanetPair._draw_trail`). 굵기가 선분마다 달라야 해서 `draw_polyline` 대신
개별 `draw_line` 으로 그린다 — 폴리라인은 굵기가 하나뿐이다.

트레일은 **'기록'이지 '구동'이 아니다.** 매 프레임 위치를 남기기만 하고
아무것도 움직이지 않으므로 규칙 3(시간축 하나)을 깨지 않는다.
축 행성은 안 움직이므로 같은 자리가 쌓이지 않도록 1px 미만 이동은 버린다.

python3 tools/make_song.py      # 곡 생성 (assets/song_140.wav + .json)
python3 tools/make_charts.py    # 채보 생성 (곡의 온셋을 읽는다)

140bpm 4/4 칩튠, 40마디 69.6초. 리드(구형파) + 베이스(삼각파) + 킥/스네어/하이햇.
A-B-A-C 구성에 인트로/아웃트로.

**가장 중요한 산출물은 WAV 가 아니라 `song_140.json` 의 멜로디 온셋이다.**
채보 생성기가 그걸 읽어서 타일 리듬을 만든다 — 곡과 채보가 같은 소스에서
나와야 둘이 갈라지지 않는다. 손으로 다시 적으면 반드시 어긋난다.

타일 174개 · 심판 대상 173개 · 카운트인 6.43초(인트로 4마디가 그대로 카운트인).
자동플레이 결과: **랭크 P · 100.00% · 콤보 173 · σ 2.4ms**.

### 곡을 만들 때 지켜야 하는 제약

**한 타일이 표현할 수 있는 대기는 (0, 2] 박이다.** `sweep` 이 (0, 360] 이고
`beats = sweep/180` 이기 때문이다. 3박 쉼표는 한 타일로 못 만든다.

처음 만든 곡의 아웃트로에 9박 공백이 있었는데 `make_song.py:verify()` 가 잡았다.
2박짜리 롱톤으로 채워서 해결했다. 곡을 새로 만들 때마다 이 검증이 돌아간다.

### 토끼 / 달팽이 타일

얼불춤의 `SetSpeed`. `Chart.speed_changes` 에 `(타일 인덱스, 배율)` 로 넣는다.
배율은 누적이 아니라 대체다 — 그 타일의 배속을 바로 읽을 수 있어야 디버깅이 된다.

song140 에는 C 구간(28마디)에 토끼 x1.5, 아웃트로에서 원복, 마지막 두 마디에
달팽이 x0.7 이 걸려 있다. 위 삼각형 = 빨라짐, 아래 삼각형 = 느려짐.

**여기서 앞서 만든 판정창 캡이 값을 한다.** 배속이 오르면 타일 간격이 좁아지는데,
`Judge.set_gaps` 가 판정창을 이웃까지 거리로 캡하므로 자동으로 같이 좁아진다.
테스트로 잠갔다 — 4배속 구간(간격 125ms)에서도 판정창(112ms)이 이웃에 안 닿는다.

### Twirl — 경로 다양성의 유일한 수단

`0.5박 홉은 CCW 에서 항상 -90도(우회전)로 꺾인다.` 8분음이 네 번 연속되면
닫힌 사각형이다. song140 에는 0.5박이 80개라 경로가 통째로 루프투성이였다.

twirl 은 회전 방향을 뒤집는다. 그러면 **같은 박자가 반대로 꺾인다**:

```
CCW:  cur = prev + 180 + b*180      0.5박 -> prev - 90 (우회전)
CW :  cur = prev + 180 - b*180      0.5박 -> prev + 90 (좌회전)
```

리듬은 그대로고 모양만 바뀐다. 착지 불변식도 양쪽 다 성립한다
(끝각이 어느 방향이든 `angles[i-1]`). 테스트로 잠갔다.

`tools/make_charts.py` 가 자동 배치한다: 누적 회전이 임계를 넘기 전에 뒤집는다.
임계값을 재봤다 (song140, 카메라 창 ±5):

| loop_guard | twirl 수 | 경로 낭비 |
|---|---|---|
| 90° | 77 (44%) | 3.28x |
| 180° | 39 (23%) | 1.76x |
| **270°** | **28 (16%)** | **1.46x** |
| 360° | 21 (12%) | 4.39x |

비단조다. 너무 자주 뒤집으면 지그재그가 촘촘해져 경로가 길어지고,
너무 드물면 루프가 돌아온다. 270° = 원을 3/4 그리기 전에 뒤집는다.

> 처음 180° 로 짰을 때 twirl 이 39개(22.5%) 나왔는데, 실제 얼불춤 채보를
> 실측했을 때가 787/3158 = **24.9%** 였다. 루프 방지라는 기하학적 필요만으로
> 짠 휴리스틱이 원작과 같은 밀도에 도달했다. 같은 제약에서 나온 같은 답이다.

**twirl 이 카메라 문제도 같이 풀었다.** 경로가 덜 루프지니 창을 좁혀도 된다:

| | 카메라 창 | 경로 낭비 | 행성거리 |
|---|---|---|---|
| twirl 전 | ±5 (한계) | 4.75x | 274px |
| **twirl 후** | **±3** | **1.75x** | **241px** |

두 지표가 동시에 개선됐다. 카메라를 아무리 튜닝해도 못 넘던 벽이었는데
원인이 카메라가 아니라 경로였다.

### (해결됨) 경로가 너무 루프를 그린다

`0.5박 홉은 항상 같은 방향으로 -90도 돈다.` 8분음이 네 번 연속되면 닫힌 사각형이다.
song140 에는 0.5박이 80개라 경로가 demo 보다 훨씬 루프가 많고, 카메라가 그만큼 흔들린다.

| 채보 | 카메라 창 ±2 | ±5 | ±8 |
|---|---|---|---|
| demo | 3.32x / 194px | — | — |
| song140 | 7.35x / 212px | **4.75x / 274px** | 2.50x / 370px |

뷰포트 반높이가 360px 라 ±8 부터는 행성이 화면 밖으로 나간다. 그래서 ±5 가 상한이고,
그 상태에서도 4.75x 다.

**근본 해결은 카메라가 아니라 twirl 이다.** 실제 얼불춤 채보가 타일의 25% 에
twirl(회전방향 반전)을 거는 게 정확히 이것 때문이다 — twirl 이 있어야 연속 8분음이
원이 아니라 지그재그가 된다. 아직 미구현.

| 등급 매핑 | +45ms → LATE PERFECT · −45 → EARLY PERFECT · ±85 → LATE!/EARLY! · 0 → PERFECT |
| 무입력 | 감시자가 TOO_LATE 를 낸다 |
| 키 리피트 | 같은 프레임에 echo 3회를 보내도 타일이 1칸만 전진 |
| 워밍업 중 입력 | 무시되고 산포 표본을 오염시키지 않는다 |
| 곡 종료 후 입력 | 5회 눌러도 크래시 없음 |
| R 재시작 | idx·finished·점수 초기화, **산포 표본은 유지**, 클럭 카운터 리셋 |

### 발견: 입력 경로에 +11ms 편향이 있다

실측이 전부 + 방향으로 치우친다 — 의도 0ms 가 +8.8\~12.3, −45 가 −33.1, −85 가 −72.3.

그중 ~7ms 는 하네스가 프레임마다 폴링해서 최대 한 프레임 늦게 누르는 탓이고,
나머지가 엔진 입력 디스패치다. 실제 키보드는 여기에 하드웨어/OS 지연이 더 붙는다.

**캘리브레이션 슬라이더를 + 방향으로 밀어야 한다는 설계 예측과 정확히 맞는다.**
사람이 칠 때 평균이 얼마나 치우치는지가 다음 측정 대상이다.

## 경로를 낱개 타일로 그린다

원래 `Line2D` 연속 획이었다. 타일로 바꾼 건 장식이 아니라 **조작 편의** 때문이다.

연속선은 다음에 어디서 밟는지를 눈으로 셀 수 없다. 타일이 나뉘어 있으면
**남은 개수가 그대로 남은 박자 수**라서 타이밍을 눈으로 준비할 수 있다.
원작이 타일로 그리는 이유가 이것이다.

각 타일은 한 변이 간격과 같은 정사각형이고 그 타일에서 나갈 방향으로 회전한다.
직선 구간에서는 중심 간격 == 한 변이라 정확히 맞닿는다. 꺾이는 데선 안쪽이 겹치고
바깥이 벌어지는데 원작도 같은 모양이다.

**타일은 채우기가 아니라 윤곽선으로 읽힌다.** 안은 거의 비어 있고(alpha 0.10~0.22)
테두리만 밝다. 테두리 색 성분을 1.0 넘게 주면(HDR) `WorldEnvironment` 글로우가 걸려서
선이 발광한다. 채우기를 불투명하게 하면 경로가 벽처럼 보여서 그 느낌이 안 난다.

상태별로 다르게 칠한다 — 이게 있어야 '지금 밟아야 할 타일'이 눈에 들어온다:

| 상태 | 채우기 | 테두리 |
|---|---|---|
| 지나감 | 0.10 alpha | 어둡게 (0.35, 0.42, 0.62) |
| 앞으로 올 것 | 0.14 alpha | HDR (1.15, 1.35, 1.90) |
| **지금 목표** | 0.22 alpha | **HDR (2.20, 2.00, 1.10)** · 굵기 3.5 |

### 타일 임팩트

밟은 타일이 **판정 색으로 부풀면서 사라진다**(0.22초). 방사 플레어도 같이 터진다.
커졌다 돌아오는 게 아니라 커지면서 사라져서 잔상처럼 읽힌다.

색이 곧 판정이다: Perfect 초록 · E/L Perfect 연두 · Very 노랑 · Miss 빨강.
어느 타일을 어떻게 밟았는지가 경로 위에 남아서, 다음 구간을 준비하면서도
직전 결과를 읽을 수 있다.

임팩트는 순수 연출이라 오디오 클럭이 아니라 프레임 시간으로 감쇠시킨다
(화면 흔들림과 같은 취급). 활성 임팩트가 없으면 `set_process(false)` 로 멈춘다 —
174개 타일을 이유 없이 매 프레임 다시 그리지 않는다.

## 화면 요소

### 중앙 상단 — 판정 + 콤보

시선이 경로를 따라 움직이므로 판정을 타일 옆에만 띄우면 놓친다.
**화면에 고정된 자리가 하나 필요하다.** 판정 이름과 콤보 숫자를 판정 색으로 띄운다.

### 시작 카운트다운

인트로가 16박이라 전부 세면 지루하다. **첫 타일까지 4박 남았을 때부터** 센다
(`Main.COUNTDOWN_BEATS`). 박자마다 밝기가 살아나고 마지막에 `GO`.

### 완주 결과 화면

랭크 · 정확도 · 판정 분포(너무 빠름 / 빠름 / 빠름! / 정확 / 느림! / 느림 / 너무 느림) ·
최대 콤보 · **판정 오차 평균과 표준편차**.

마지막 두 개가 중요하다: 평균이 치우쳤으면 오프셋 슬라이더로 고칠 수 있고,
표준편차가 크면 못 고친다. 결과 화면이 그 구분을 매번 보여준다.

정확도별 문구: 100% 완벽한 플레이 · 99%+ 거의 완벽 · 95%+ 훌륭한 클리어 ·
90%+ 클리어 · 70%+ 완주 · 그 아래 다시 해보자.

### 실패 조건

정확도가 `fail_below_accuracy`(기본 55%) 아래로 떨어지면 끝난다.
단 **유예 판정 수**(기본 12)를 넘긴 뒤부터 본다 — 판정이 적을 때는 한 번만 놓쳐도
정확도가 크게 흔들려서, 초반 미스 한두 번으로 끝나면 가혹하다.

무입력으로 두면 정확히 12판정 뒤에 실패한다. 스모크가 그걸 검증한다
(자동플레이일 때만 완주를 요구하고, 무입력이면 실패를 요구한다).

### 지나간 타일이 떨어져 나간다

원작의 `trackDisappearAnimation`. 밟고 지나간 타일이 중력으로 떨어지며 회전하고
1.15초에 걸쳐 사라진다. 다 떨어진 타일은 아예 안 그린다.

난수(초기 속도·각속도)는 **떨어지기 시작할 때 한 번만 뽑아 저장한다.**
매 프레임 뽑으면 타일이 제자리에서 부들거린다.

한 프레임에 여러 칸 전진할 수도 있으므로(랙 스파이크) `set_cursor` 가
직전 커서부터 새 커서까지 전부 떨어뜨린다.
