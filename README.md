# rhythm-godot

A Dance of Fire and Ice(얼불춤) 스타일의 **원버튼 리듬게임**. Godot 4.7 / GDScript.

두 행성이 꺾인 타일 경로를 번갈아 공전한다. 버튼은 스페이스 하나뿐이고,
낙하 노트가 없다 — **타일의 각도가 곧 대기 박자 수**라서 눈이 아니라 귀와 손으로 푸는 게임이다.

설계 배경과 결정 근거: `~/.gstack/projects/rhythm-godot/kyb-ontact-main-design-*.md`
작업 규칙(불변 규칙 · 검증 절차 · 병렬 세션 규약): [CLAUDE.md](CLAUDE.md)

## 이 게임의 심장

```
공전 각속도가 박자당 180도로 고정이면, 타일 사이 상대각이 곧 대기 시간이다.

         prev+180 (공전 시작)
              \
               \   sweep
                \ ,-'`
        [pivot]  o------> cur (다음 타일 방향)

    sweep = fposmod(cur - (prev + 180), 360)     # 0 이면 360
    beats = sweep / 180

    직선 (cur==prev)     -> sweep 180 -> 1.0박
    U턴  (cur==prev+180) -> sweep 360 -> 2.0박
    90도 꺾임            -> sweep 270 -> 1.5박
```

따라서 **노트 타임라인이라는 자료구조가 아예 필요 없다.** 각도 배열 하나가
렌더와 타이밍을 동시에 생성한다. 두 개의 진실 소스가 없으므로 둘이 어긋날 수 있는
버그 표면 자체가 사라진다. (대부분의 클론이 여기서 어긋난다.)

### 이 공식은 실측 검증됐다

```bash
python3 tools/verify_formula.py <실제 .adofai 파일들>
```

- ADOFAI 기본 레벨(직선 10타일 @ bpm 100) → **정확히 1.0박 / 600ms 간격**
- 실제 채보 3,155타일 → 최빈값이 정확히 1.0(34%), 모든 값이 1/12 격자, 쓰레기 값 0
- 반증 대조군: `+180` 을 빼면 직선이 **2박**이 되어 즉시 탈락

검증 중 알게 된 것 3가지:

1. **`.adofai` 는 유효한 JSON 이 아니다.** 실제 파일에서 위반 3종 발견 —
   이중 콤마(`"difficulty": 1, ,`), 트레일링 콤마, 섹션 간 콤마 누락.
   `tools/verify_formula.py:load_adofai()` 가 이걸 감안해 읽는다.
2. **CCW/CW 규약은 이 증거로 결정되지 않는다.** 두 변형이 직선·U턴에서 같고
   좌/우 회전에서만 갈린다(1.5 ↔ 0.5). 우리가 채보를 직접 짜므로 무관하지만,
   실제 `.adofai` 를 로드하려면 정해야 한다.
3. **실제 채보는 이 프로젝트가 모델링하는 것보다 훨씬 복잡하다.**
   샘플 채보는 SetSpeed 132개(bpm 128→512)에 Twirl 이 타일의 25%.
   → "직접 짠 채보만 쓴다"는 결정이 옳았다는 증거다.

```

└── AudioStreamPlayer            클럭이 자기 재생 노드를 소유한다

Main.tscn                        씬 리로드로 재시작해도 안전
├── World
│   ├── Camera2D                 위치도 오디오 클럭에서 파생
│   ├── Path (Line2D)            각도 배열을 그대로 그린 경로
│   ├── PlanetPair               set_orbit_progress(u) — Tween 없음
│   │   ├── PlanetA / PlanetB
│   └── JudgmentPopup
├── Judge                        판정창 3개가 @export
└── UI
    ├── CalibrationPanel         오프셋 슬라이더 ±150ms
    └── DebugOverlay             표본·평균·표준편차·clamp_hits·output_latency
```

| 스크립트 | 역할 |
|---|---|
| `ChartRuntime.gd` | 각도→박자·좌표. **순수 static 함수만.** 단위 테스트 대상은 여기뿐 |
| `Chart.gd` | Resource. 채보의 단일 진실 소스 |
| `AudioClock.gd` | 오디오 클럭 + 재생 소유. autoload |
| `Judge.gd` | ms 판정만. 렌더도 상태 전진도 모름 |
| `Main.gd` | 배선 + TileCursor 상태 + 감시자/입력자 |

### 지키는 규칙 8개

**1. 판정은 오디오 클럭 ms 차이로만 한다.** 좌표 겹침도 프레임 카운트도 안 쓴다.

```gdscript
var ms := (get_playback_position() + AudioServer.get_time_since_last_mix()
           - AudioServer.get_output_latency()) * 1000.0
_last_ms = maxf(ms, _last_ms)   # 스레드 지터로 역행할 수 있다(공식 문서 경고)
```

`get_playback_position()` 만 쓰면 오디오 스레드가 다음 청크를 믹싱할 때까지 같은 값을
돌려주므로 클럭이 믹스 버퍼만큼의 계단으로 뚝뚝 뛴다. 그 계단폭이 그대로 판정 잡음이 된다.

**2. `now_ms()` 는 `_input()` 과 `_process()` 각각에서 그 자리에서 부른다. 캐시 금지.**
`_process` 에 캐시한 값을 `_input` 에서 쓰면 최대 1프레임(60fps 에서 16.7ms)이
판정 오차로 그냥 들어간다.

**3. 시간축은 하나뿐이다. `Tween` 을 쓰지 않는다.**
Tween 은 프레임 루프가 굴리는 벽시계라 오디오 클럭과 별개의 두 번째 시간축이 된다.
가장 흔한 증상은 크래시가 아니라 **"행성은 아직 도착 안 했는데 판정은 Perfect"** —
눈과 손이 불일치하는, 진단이 가장 어려운 종류다.
공전각도 카메라 위치도 전부 `now_ms()` 에서 파생시킨다.

같은 이유로 **캘리브레이션 오프셋을 클럭 안에서 빼지 않는다.** 클럭 안에서 빼면
슬라이더를 미는 순간 ① `clamp_hits` 가 올라가고(하드 게이트의 거짓양성)
② `maxf` 가 이전 값을 붙잡아 클럭이 오프셋만큼 얼어붙는다. 오프셋은 판정 시점에 뺀다.

**4. 렌더 커서와 판정 커서는 별개다. 둘 다 `now_ms()` 에서 파생되지만 전진 조건이 다르다.**

| 커서 | 전진 조건 | 쓰는 곳 |
|---|---|---|
| `_idx` (판정) | 입력이 오거나 `hit_time + miss_ms` 경과 | 판정, 판정창 |
| `_vis` (렌더) | `t >= hit_time` — 그냥 시간이 지나면 | 공전각, 카메라, 팝업 위치 |

묶어두면 **행성이 매 타일 `miss_ms` 만큼 얼어붙는다.** 감시자는 늦은 입력을 받아주려고
기한까지 기다려야 하는데, 렌더가 그걸 따라가면 u=1.0 에 붙어서 멈춘다.

실측: 렌더를 판정 커서에 묶으면 전체 프레임의 **25.8%** 가 정지 상태다
(0.5박@120bpm 구간은 250ms 중 110ms = 44%). 분리하면 **0.7%** 로 떨어진다.
`tests/SmokeRunner.gd` 가 이 비율을 재서 8% 를 넘으면 실패시킨다.

**5. 카메라는 순간 위치가 아니라 '주변 타일의 평균'을 본다.**

행성이든 축이든 중점이든, **순간 위치를 쫓으면 경로의 지그재그를 그대로 따라가서
위아래로 튄다.** demo 채보만 해도 90도 4연속(사각형)이 두 번, U턴이 세 번 있어서
길이 진짜로 되돌아온다. 알고리즘 문제가 아니라 경로 문제다.

그래서 앞뒤 ±2 타일의 평균을 본다(`Main.CAMERA_WINDOW`). 사각형 구간이면
사각형 중심에 머문다. 창이 대칭이라 앞으로 올 타일도 반영된다(선행 시야).
타일 사이는 `u` 로 연속 보간해서 타깃이 계단으로 뛰지 않게 한다.

실측 — 경로 낭비 배수(실제 이동거리 / 순 이동거리, 1 이면 곧게 따라감):

| 카메라 타깃 | 프레임이동 최대 | 낭비배수 | 행성까지 최대 |
|---|---|---|---|
| 타일 사이 직선 lerp | 29.35 px | 5.86x | 147 px |
| 두 행성 중점 | 5.11 px | **8.17x** | 48 px |
| 축(현재 타일)만 | 96.00 px | 6.50x | 96 px |
| **주변 타일 평균 ±2** | **3.09 px** | **2.65x** | 194 px |

중점은 위치 연속성은 최고였지만(축 주위 반지름 48px 원) 오히려 가장 많이 흔들렸다.
두 지표를 같이 안 보면 한쪽을 고치면서 다른 쪽을 망친다.

창 크기 트레이드오프: ±1 은 4.07x/162px · ±2 는 3.32x/194px · ±3 은 3.10x/242px.
크게 잡을수록 차분하지만 행성이 화면 중심에서 멀어진다.

흔들림(미스 연출)은 `position` 이 아니라 `offset` 으로 준다 — `position` 에 실으면
`position_smoothing` 이 뭉개서 '흔들림'이 아니라 '느린 표류'가 된다.

**6. 미스마다 화면을 흔들지 않는다. 콤보가 실제로 끊길 때만 짧게 흔든다.**

리듬게임에서 미스는 흔한 일이다. 흔들림이 타일 간격(250~500ms)보다 길면
사실상 상시 진동이 된다. 실측: 14px/233ms 로 매 미스마다 흔들었더니
**전체 프레임의 47.3%** 가 흔들리고, 화면에 보이는 경로 낭비가
2.65x -> **18.01x** 로 뛰었다.

그리고 `randf()` 로 매 프레임 방향을 바꾸면 안 된다. 144fps 면 초당 144번
방향이 바뀌어서 '충격'이 아니라 '떨림'으로 읽히고, fps 에 따라 체감도 달라진다.
고정 주파수(22Hz) 감쇠 진동을 쓴다.

| | 흔들리는 프레임 | 보이는 경로 낭비 |
|---|---|---|
| 미스마다 14px/233ms · 매 프레임 랜덤 | 47.3 % | 18.01x |
| **콤보 3+ 끊길 때만 7px · 22Hz** | **4.5 %** | **3.06x** |

> **계측 함정:** 흔들림을 `offset` 으로 옮긴 뒤에도 지표는 `position` 만 재고 있었다.
> 그래서 "카메라 낭비 2.65x, 통과"라고 보고했는데 실제로 보이는 값은 18.01x 였다.
> 지금은 **연속성은 `position`, 흔들림은 `position + offset`** 으로 나눠 잰다.
> 섞으면 정당한 흔들림이 연속성 실패로 오인된다.

**7. 채보에는 카운트인이 있어야 한다 (기본 4박).**

음악적으로도 필요하지만 기술적으로도 필요하다. `AudioClock` 워밍업(100ms) 동안
렌더가 멈춰 있는데, 첫 타일이 0ms 에 있으면 warm 되는 순간 그만큼을 한 번에
건너뛰어 카메라가 32px 튄다. `tools/make_charts.py:LEAD_IN_BEATS`.

**8. 인덱스는 `angles[i-2]`(들어온 방향)와 `angles[i-1]`(나갈 방향)이다. `angles[i]` 가 아니다.**

타일 `i` 로 가는 공전은 축이 타일 `i-1` 이고, 도는 행성이 타일 `i-2` 에서 출발해
타일 `i` 에 착지한다. 그러니 스윕을 정하는 건 `angles[i-2]` 와 `angles[i-1]` 이다.
`angles[i]` 는 타일 `i` 에서 그 다음으로 나갈 방향이라 한 칸 미래다.

첫 구현이 여기서 한 칸 밀려 있었다. **직선 구간에선 착지 오차가 정확히 0 이라
전혀 안 보이고**, 꺾이는 데서만 드러난다:

| 경로 | 밀렸을 때 착지 오차 | 고친 뒤 |
|---|---|---|
| 직선 | 0.00 px | 0.00 px |
| 90도 계단 | 135.76 px | 0.00 px |
| 사각형(90도 4연속) | 135.76 px | 0.00 px |
| U턴 | 192.00 px | 0.00 px |

타일 간격이 96px 이니 최대 두 칸을 벗어난 채 내렸다가 튄 것이다.
`tests/run_tests.gd:t_landing()` 이 여섯 가지 경로 모양에 대해 좌표로 잠근다.
`tools/make_charts.py` 도 채보를 만들 때마다 같은 불변식을 잰다.

## 실행

```bash
# 곡(메트로놈 클릭) 생성 — BPM 이 샘플 단위로 정확해야 한다
python3 tools/make_click.py 120 60

# 채보 생성 — 각도를 손으로 안 쓴다. 박자 패턴에서 역산한다
python3 tools/make_charts.py

# 변환기 단위 테스트 (파서 · 밀도 보강 · 걸음 채움)
python3 tools/test_midilib.py
python3 tools/test_density.py

# 단위 테스트 (의존성 0) — 85종
godot --headless --script res://tests/run_tests.gd

# 통합 스모크 (전곡 완주 · 감시자 · 곡종료 · 클럭 역행 · 카메라 · 흔들림)
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn

# 자동 플레이 — 판정 체인 전체 검증 (랭크 P / 100% / σ 2.1ms 가 나와야 한다)
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn -- --autoplay

# 일부러 놓치기 — 콤보 끊김과 흔들림 발동 검증
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn -- --autoplay --miss-every=5

# 체크포인트 부활 (seek 뒤 클럭이 얼지 않는지 — 단위 테스트로는 못 잡는다)
godot --headless --audio-driver CoreAudio res://tests/CheckpointScene.tscn

# 홀드 타일 (뗌 판정 · 히트타임 밀림 · 착지 불변식)
godot --headless --audio-driver CoreAudio res://tests/HoldScene.tscn

# 조작 표면 — 등급 매핑 · echo 필터 · R 재시작 · 워밍업/종료 후 입력
godot --headless --audio-driver CoreAudio res://tests/InputScene.tscn

# 리플레이 — 판정 기록의 비트 단위 재현 (원판 == 재생, 원소 단위 비교)
godot --headless --audio-driver CoreAudio res://tests/ReplayScene.tscn

# 오토플레이 데모 — 전 타일 delta 0 · P 100% 약속을 잠근다
godot --headless --audio-driver CoreAudio res://tests/AutoScene.tscn

# 곡 선택 화면 — 목록·키·토글
godot --headless res://tests/SelectScene.tscn

# 오디오 클럭 실측 (드리프트·지터·3항vs1항)
godot --headless --audio-driver CoreAudio --script res://tests/probe_clock.gd

# 실행
godot -e     # 에디터
godot        # 바로 실행
```

**조작:** `스페이스` 판정 · `R` 재시작

### 곡을 왜 만들어 쓰나

음악은 BPM 이 정확히 알려져 있지 않거나 변속이 있거나 그루브가 있다. 판정이 어긋났을 때
원인이 내 코드인지 곡인지 구분이 안 된다. 클릭은 샘플 단위로 정확하다 —
실측 결과 간격 오차 최대 0.042ms, 60초 누적 드리프트 +0.08ms.

WAV 를 쓰는 이유: 손실 압축은 어택 트랜지언트를 뭉갠다. 디코더 지연 편차도 없다.
용량이 크므로 gitignore 하고 생성기만 커밋한다.

### 성공 기준

1. 30초 이상 완주 + **연속 3회 재시작**해도 판정 동일 (`_last_ms` 리셋 검증)
2. 오프셋 슬라이더 ±150ms, 다음 판정부터 즉시 반영

   - 미달 시: 즉시 실패로 보지 말고 오디오 백엔드·버퍼·`output_latency` 실측값부터 로그.
     백엔드를 바꿔도 안 줄면 그건 코드 결함이 아니라 기계의 바닥이다.
     **코드 결함과 기계 바닥을 구분하는 게 목적이지 15라는 숫자가 목적이 아니다.**
4. **클럭 역행의 *크기*가 한 믹스 청크(~6ms)를 넘지 않을 것.** 횟수가 아니다.
   - 실측: 20초 재생에 역행 20회, 최대 5.7ms. **0 이 아닌 게 정상이다.**
     `get_playback_position()` 과 `get_time_since_last_mix()` 가 서로 독립적으로
     갱신돼서, 믹싱 직후에 샘플링하면 옛 `pos` 에 리셋된 `since_mix` 가 붙는다.
     구조적으로 일어나는 일이고 단조 클램프가 바로 그걸 막으라고 있다.
   - `get_output_latency()` 를 시작 시점에 고정해봐도 크기가 그대로였다 —

## 판정과 점수

### 7등급 (얼불춤 체계)

```
TooEarly · VeryEarly · EarlyPerfect · Perfect · LatePerfect · VeryLate · TooLate
```

Perfect 가 3종(E/일반/L)이고 **일반 Perfect 만 정확도 만점**이다. 이게 있어야
"다 맞혔지만 살짝씩 어긋난" 플레이와 "정확한" 플레이가 구분되고, 손맛을
개선했는지 알 수 있다. 랭크는 `P / SS / S / A / B / C / D / F` —
P 는 전부 일반 Perfect 일 때만 나온다.

### 판정창은 BPM 에 따라 좁아진다

고정 ±110ms 로 두면 **인접 타일 간격이 220ms 밑으로 내려가는 순간 판정창이 겹쳐서
한 번 누른 입력이 두 타일 모두에 유효해진다.**

| 박자 | bpm | 간격 | 고정창(±110) 여유 |
|---|---|---|---|
| 0.5박 | 120 | 250ms | +30ms (아슬아슬) |
| 0.5박 | 140 | 214ms | **−6ms 겹침** |
| 1/6박 | 340 | 29ms | **−191ms 붕괴** |

그래서 판정 사다리 전체를 **이웃 타일까지 거리의 절반**으로 캡한다
(`Judge.set_gaps()`). 겹침이 구조적으로 불가능해지고, 등급 간 비율은 보존된다.
얼불춤도 같은 이유로 "빠를수록 엄격"하게 만든다.

`tests/run_tests.gd:t_judge_windows()` 가 250·214·125·29·8ms 간격에서
창 폭이 간격을 절대 못 넘는지 잠근다.

### HUD

- **TimingScale 바** — 가운데가 정확, 왼쪽이 빠름. 최근 40개 입력이 눈금으로 찍히고
  파란 삼각형이 평균이다. **연출이자 계측 도구다**: 눈금이 한쪽으로 쏠렸으면
  오프셋 문제(슬라이더로 고쳐짐), 가운데를 중심으로 넓게 퍼졌으면 산포 문제(안 고쳐짐).
  판정창이 좁아지면 바 축척도 같이 확대돼서 눈금이 뭉치지 않는다.

## 테스트 제약

**`--script` 모드에선 autoload 가 등록되지 않는다.** `AudioClock` 식별자를 못 찾아서
`Main.gd` 자체가 컴파일에 실패한다. 그래서 `Main` 을 태우는 통합 테스트는
`--script` 가 아니라 **씬**(`tests/SmokeScene.tscn`)으로 만들어 정상 실행 경로에 태운다.
순수 함수만 보는 `run_tests.gd` 는 `class_name` 글로벌만 쓰므로 `--script` 로 된다.

### 잔상 트레일

두 행성이 지나간 자리를 22프레임 남긴다. 오래된 쪽이 얇고 투명해진다

축 행성은 안 움직이므로 같은 자리가 쌓이지 않도록 1px 미만 이동은 버린다.

### 곡을 만들 때 지켜야 하는 제약

**한 타일이 표현할 수 있는 대기는 (0, 2] 박이다.** `sweep` 이 (0, 360] 이고
`beats = sweep/180` 이기 때문이다. 3박 쉼표는 한 타일로 못 만든다.

처음 만든 곡의 아웃트로에 9박 공백이 있었는데 `make_song.py:verify()` 가 잡았다.
2박짜리 롱톤으로 채워서 해결했다. 곡을 새로 만들 때마다 이 검증이 돌아간다.

### 토끼 / 달팽이 타일

얼불춤의 `SetSpeed`. `Chart.speed_changes` 에 `(타일 인덱스, 배율)` 로 넣는다.
배율은 누적이 아니라 대체다 — 그 타일의 배속을 바로 읽을 수 있어야 디버깅이 된다.

song140 에는 C 구간(28마디)에 토끼 x1.5, 아웃트로에서 원복, 마지막 두 마디에
달팽이 x0.7 이 걸려 있다. 위 삼각형 = 빨라짐, 아래 삼각형 = 느려짐.

**여기서 앞서 만든 판정창 캡이 값을 한다.** 배속이 오르면 타일 간격이 좁아지는데,
`Judge.set_gaps` 가 판정창을 이웃까지 거리로 캡하므로 자동으로 같이 좁아진다.
테스트로 잠갔다 — 4배속 구간(간격 125ms)에서도 판정창(112ms)이 이웃에 안 닿는다.

### Twirl — 경로 다양성의 유일한 수단

`0.5박 홉은 CCW 에서 항상 -90도(우회전)로 꺾인다.` 8분음이 네 번 연속되면
닫힌 사각형이다. song140 에는 0.5박이 80개라 경로가 통째로 루프투성이였다.

twirl 은 회전 방향을 뒤집는다. 그러면 **같은 박자가 반대로 꺾인다**:

```
CCW:  cur = prev + 180 + b*180      0.5박 -> prev - 90 (우회전)
CW :  cur = prev + 180 - b*180      0.5박 -> prev + 90 (좌회전)
```

리듬은 그대로고 모양만 바뀐다. 착지 불변식도 양쪽 다 성립한다
(끝각이 어느 방향이든 `angles[i-1]`). 테스트로 잠갔다.

`tools/make_charts.py` 가 자동 배치한다: 누적 회전이 임계를 넘기 전에 뒤집는다.
임계값을 재봤다 (song140, 카메라 창 ±5):

| loop_guard | twirl 수 | 경로 낭비 |
|---|---|---|
| 90° | 77 (44%) | 3.28x |
| 180° | 39 (23%) | 1.76x |
| **270°** | **28 (16%)** | **1.46x** |
| 360° | 21 (12%) | 4.39x |

비단조다. 너무 자주 뒤집으면 지그재그가 촘촘해져 경로가 길어지고,
너무 드물면 루프가 돌아온다. 270° = 원을 3/4 그리기 전에 뒤집는다.

> 처음 180° 로 짰을 때 twirl 이 39개(22.5%) 나왔는데, 실제 얼불춤 채보를
> 실측했을 때가 787/3158 = **24.9%** 였다. 루프 방지라는 기하학적 필요만으로
> 짠 휴리스틱이 원작과 같은 밀도에 도달했다. 같은 제약에서 나온 같은 답이다.

**twirl 이 카메라 문제도 같이 풀었다.** 경로가 덜 루프지니 창을 좁혀도 된다:

| | 카메라 창 | 경로 낭비 | 행성거리 |
|---|---|---|---|
| twirl 전 | ±5 (한계) | 4.75x | 274px |
| **twirl 후** | **±3** | **1.75x** | **241px** |

두 지표가 동시에 개선됐다. 카메라를 아무리 튜닝해도 못 넘던 벽이었는데
원인이 카메라가 아니라 경로였다.

### 경로 계획 — loop_guard 를 빔서치로 교체 (2026-08-07)

실곡을 여러 개 넣자 loop_guard 의 한계가 드러났다. 누적 회전만 보므로 원은
못 그리게 해도 **경로가 자기 위로 되돌아오는 건 못 막는다** — 실측 겹침
(비인접 타일 쌍, 중심거리 < 0.92변) 이 곡당 564~4,902쌍이었다.

`make_charts.plan_path` 가 교체했다. 빔서치(폭 64, 난수 없음)로 홉마다
회전 방향을 고르고, 비용은 '새 타일이 기존 타일과 얼마나 겹치나'다.
리듬은 손대지 않는다 — 고를 수 있는 건 모양뿐이다.

**2박 홉은 스핀 선택으로도 못 푼다.** 스윕이 정확히 360도라 방향과 무관하게
`나갈 방향 = 들어온 방향 + 180`, 즉 항상 U턴이다. 채움 타일이 2박 걸음으로
이어지는 곡(mureka_07: 홉의 68%)은 경로가 두 지점을 왕복하며 같은 자리에
수십 장씩 쌓였다. 그래서 타일 종류를 하나 늘렸다:

**고스트(자동 통과) 타일** — `Chart.ghost_tiles`. 2박 대기를 1박+1박으로
쪼개고 중간 타일은 밟지 않는다. 1박 홉은 직선이므로 채움 체인이 왕복 스택
대신 직선 행진이 된다. 탭 리듬은 그대로다 (셋의 타이밍 검증이 전부 잠근다:
Python 되계산 vs 템포맵 정답 < 0.01ms · GDScript verify_chart.gd · 밟는
타일의 누적박 == 온셋 누적). 판정 커서는 고스트를 건너뛰고(`Main._advance`),
판정창 캡도 '판정되는 이웃'까지의 거리로 잰다. 렌더는 절반 크기 흐린
윤곽 — 빛나는 건 전부 '칠 것'이라는 규약을 지킨다.

**반복 구간은 패턴 템플릿으로 짠다 (창작마당 어휘).** 같은 홉이 3번 이상
이어지는 구간(스트림·채움 체인)을 홉 단위 탐욕으로 풀면 스핀이 잡음처럼 튀어
무늬가 안 된다. 그래서 반복 구간은 템플릿 통째로 분기시킨다 — 지그재그 ·
2/3주기 파도 · 상수 스핀 호(나선), 2박 체인은 직선 행진 · 계단 · 사다리 ·
U턴 왕복. 충돌 비용은 똑같이 적용되므로 막힌 자리에선 그 패턴이 자연히
탈락한다. 8홉 단위로 잘라 빔이 경계에서 무늬를 갈아탈 수 있다.

결과: 19곡 겹침 합계 25,516 → 1,062쌍 (**평균 96% 감소**). 남는 건
1/12박 스트림의 기하학적 고유 겹침(15도 스윕 = 어느 쪽으로도 165도 꺾임)
뿐인데, 규칙적이라 원작의 고속 구간처럼 읽힌다.

loop_guard 는 `angles_from_hops` 에 남아 있다(테스트/데모 채보용).
곡 채보(`chart_from_song`)는 전부 플래너를 탄다.

### 중간회전(midspin) — 없던 자유도 (2026-08-10)

밀도를 올리자 촘촘한 곡의 경로가 코일이 됐다(mureka_06 395쌍 · mureka_08 305쌍).
플래너를 아무리 손봐도 안 풀렸는데, 이유가 명확했다:

**홉마다 고를 수 있는 게 회전 방향 하나뿐이었다.** 리듬이 회전 '크기'를
강제하므로(각도 = 박자 x 180도) 짧은 홉은 무조건 큰 꺾임이다:

```
0.25박 홉 -> 스윕 45도 -> 진행방향이 225도(=-135도) 꺾인다 -> 네 번이면 제자리
```

얼불춤에는 하나 더 있다. **중간회전** — 타일에 도달했을 때 두 행성이 역할을
교대하지 않고 이어서 돈다. 그러면 공전 시작각이 180도 달라진다:

```
보통     나갈방향 = 들어온방향 + 180 + spin*b*180
중간회전  나갈방향 = 들어온방향       + spin*b*180
```

**박자는 그대로인데 기하만 뒤집힌다.** 같은 0.25박이 225도 대신 **45도** 꺾임이
되어, 코일이 될 스트림이 완만한 호로 펴진다. 리듬을 한 톨도 안 건드리고
경로만 바꾸는 유일한 수단이다.

| | 겹침(쌍) |
|---|---|
| loop_guard 휴리스틱 | 25,516 |
| 빔서치 + 고스트 + 패턴 | 1,504 |
| **+ 중간회전** | **19** |

곡별로도 최악이 사라졌다: mureka_06 395 → 1 · mureka_08 305 → 0 · mureka_14 278 → 2.
플래너는 홉마다 (spin x midspin) 넷을 고르고, 반복 구간에서는 스핀 무늬 하나당
중간회전 무늬 셋(없음·전부·번갈아)을 곱해 본다. `COST_MID = 1.2` 로 남발을
막는다 — 실제로 안 쓰이는 곡도 있다(song140 은 0개).

**착지 불변식이 여기서 제일 위험하다.** 시작각을 180도 옮기는 변경이라,
시작각과 스윕을 따로 고치면 행성이 타일 밖에 내린다. `spin x midspin` 4조합
전부에 대해 좌표로 잠갔다(`t_landing`, 오차 0.0000px).

표시: twirl 은 보라색 나선, 중간회전은 **청록색 겹고리**. 구분이 없으면
"왜 갑자기 반대로 도는지" 를 읽을 방법이 없다.

### 타일 종류 — 체크포인트 · 홀드 · 삼행성 (2026-08-10)

원작의 게임플레이 이벤트와 대조해 없는 것을 채웠다. 우리 **고스트 타일은
원작의 Auto Play Tiles 와 같은 물건**이었다 — 같은 제약에서 같은 답이 나왔다.

| 원작 | 우리 |
|---|---|
| SetSpeed (토끼/달팽이) · Swirl · Auto Play Tiles | 있었음 |
| — | 중간회전 (우리가 먼저 넣음) |
| **Checkpoint · Hold · Multi Planet** | **이번에 추가** |
| Beat Pause · Free Roam | 아직 |

#### 체크포인트 — seek 금지를 푼 이유

곡이 150~180초에 타일이 500~850개다. 80% 에서 죽으면 2분을 다시 치는데
그건 난이도가 아니라 벌이다. 체력이 바닥나면 마지막으로 지난 체크포인트
1.6초 앞에서 되살아난다(카운트인과 같은 이유 — 되살아나는 순간이 곧 판정
순간이면 손을 올릴 시간이 없다). 30초마다 하나씩, 곡당 4~6개.

**이건 seek 를 요구한다.** 그동안 "만들지 않는다"고 못박아 뒀던 경로다 —
`now_ms()` 의 단조 클램프(`_last_ms = maxf(...)`)가 시간이 안 되감긴다는
전제 위에 있어서, 그냥 `_player.seek()` 를 부르면 **클럭이 옛 값에 영원히
얼어붙는다**. 크래시가 아니라 '그 뒤 판정이 전부 미스'가 되는 조용한 고장이다.

풀이는 방어 코드가 아니라 규약이었다: 클램프는 '한 재생 구간 안에서'만
성립하는 불변식이지 곡 전체의 것이 아니고, `start()` 는 이미 매 재생마다
이력을 버리고 있다. `AudioClock.seek()` 가 같은 리셋을 하면 새 구간이
시작되는 것과 구별할 이유가 없다. `_player.seek()` 직접 호출 경로는 여전히 없다.

단위 테스트로는 절대 안 잡히는 종류라 `tests/CheckpointScene.tscn` 이
실제로 곡을 틀고, 죽이고, 되감고, **되감은 뒤 클럭이 계속 흐르는지**를 잰다
(실측: 33.3초에 사망 → 29.9초로 부활 → 클럭 정상 진행, 역행 0회).

#### 홀드 — 이 게임 최초의 두 번째 입력 동사

밟은 뒤 행성이 제자리에서 N바퀴 더 돌고, 그동안 키를 누르고 있어야 한다.
**뗌도 판정 대상**이라 홀드 하나가 판정 두 건이다(분모도 두 번 센다).

- 한 바퀴 = 스윕 360도 = **2박**. 360도의 배수라 **착지 지점이 안 바뀐다** —
  홀드를 넣어도 경로 기하가 그대로다.
- 뗌 이벤트(`pressed == false`)는 그 전까지 `_input` 첫 줄에서 통째로
  버려지던 값이라 경로가 하나 새로 생겼다. `_hold_key` 를 들고 있어야 한다 —
  판정키가 거의 모든 키라(양손 교타) '아무 키나 떼면 종료'로 하면
  다른 손의 탭이 홀드를 끊는다.
- 안 떼고 버티면 감시자가 미스로 확정한다(탭과 대칭 — 둘 다 이벤트가 없다).

**홀드는 히트타임을 뒤로 미는 유일한 타일이다.** 그래서 이미 오디오에 동기된
채보에 나중에 끼워 넣을 수 없다 — 홀드 시간은 반드시 기존 홉에서 빼와야 하는데
한 바퀴(2박)가 최대 홉(2박)과 같아서 한 홉으로는 못 만든다. 즉 **홀드는
여러 온셋을 덮어야** 하고, 그건 '지속음이 어디인가'를 아는 변환기(midi2song)의
일이다.

실곡 자동 배치는 `place_holds` 가 한다. **기본으로 켜져 있다**(끄려면 `--no-holds`).
opt-in 으로 두면 `--holds` 를 빠뜨린 재생성 한 번에 홀드가 조용히 사라지는데,
실제로 그럴 뻔했다 — 아래 전곡 적용을 돌리다가 플래그를 빠뜨린 스크립트를 먼저 만났다.
배치 규칙 세 개가 전부 음악에서 온다:

1. **지속음 위에서만** — 멜로디 노트가 실제로 2n박 이상 끌릴 때만(dur 상한).
   짧은 노트에 홀드를 걸면 소리는 끝났는데 손만 잡혀 있는 거짓 동작이 된다.
2. **뗌 -> 다음 탭 이동 시간** — 이동 구간이 보강 타일과 같은 ms 바닥(150ms)을
   넘어야 한다. 뗌도 판정이라 뗌-누름 간격은 탭-탭 간격과 같은 물리다.
3. **홀드 구간(누름~뗌)엔 아무 타일도 못 들어간다** — 잡은 손은 탭을 못 친다.
   보강·걸음 채움이 공백을 '뗌부터' 재도록 가르쳤고, 최소 간격도 뗌에서 잰다.

온셋의 절대 시각은 안 건드린다 — 다음 온셋까지의 간격 g 에서 2n박을 대기
대신 홀드로 바꾸면 2n박 홀드 + (g-2n)박 이동 = g박, 다음 타일 시각이 그대로라
원곡 오디오 정렬도 깨지지 않는다(원곡 모드의 홉 단위 템포 적합은 양 끝점
시간 보존이라 홀드 유무와 무관하게 성립한다).

실측(mureka_09, 원곡 오디오 + --holds): 홀드 24개(총 50박)가 베이스 지속음
위에 배치, 밀도 3.75 -> 3.43탭/초(홀드가 걸음 채움을 흡수), 파일 검증
0.000005ms/타일 · 엔진 0.0092ms · 오토플레이 스모크 랭크 P · 100% ·
판정 505건(타일 481 - 고스트 3 + 홀드 24x2 — 분모가 정확히 두 번 센다).
스모크 하네스도 뗌을 배웠다 — 홀드 종료 시각에 잡은 키를 놓는다.

**전곡 적용 (2026-08-10):** 14곡에 **홀드 116개 · 147바퀴**.
곡별 편차가 큰 게 정직하다 — 지속음이 많은 보컬·패드 곡은 16~24개인데
**1/12박 스트림 곡(mureka_06)은 0개**다. 끌리는 음이 없으면 홀드도 없는 게 맞다.

#### 삼행성 — 박자와 각도의 관계가 바뀐다

도는 행성이 정반대(180도)가 아니라 그보다 더 돌아간 데서 출발한다:

```
시작 오프셋 = (P-2) x 180 / P      P=2 -> 0도 · P=3 -> 60도 · P=4 -> 90도
```

원작 변환 도구(`planetamountconvert.py`)가 쓰는 식과 같다. 스윕이 그만큼
짧아지므로 **같은 기하가 더 적은 박자**가 된다 — 직선 타일이 1박에서 **2/3박**으로.
그래서 같은 채보를 행성 수만 바꿔 쓰면 곡과 통째로 어긋난다. 채보가 자기
행성 수를 들고 있어야 하는 이유고(`Chart.planet_count`), **기본값 2 에서
오프셋이 정확히 0 이라 기존 채보는 한 글자도 안 바뀐다**.

기하가 눈에 띄게 다르다: 1박을 계속 요청하면 2행성은 직선, 3행성은 **육각형**이
된다(`t07_three`, 각도 0/60/120/180/240/300). 세 번째 행성은 직전 타일에
세운다 — 연속한 두 타일은 정의상 spacing 만큼 떨어져 있어서 축에서 본 거리가
도는 행성과 같다.

착지 불변식을 오프셋 x spin x 중간회전 **12조합** 전부에 대해 좌표로 잠갔다(0.0000px).

### (해결됨) 경로가 너무 루프를 그린다

`0.5박 홉은 항상 같은 방향으로 -90도 돈다.` 8분음이 네 번 연속되면 닫힌 사각형이다.
song140 에는 0.5박이 80개라 경로가 demo 보다 훨씬 루프가 많고, 카메라가 그만큼 흔들린다.

| 채보 | 카메라 창 ±2 | ±5 | ±8 |
|---|---|---|---|
| demo | 3.32x / 194px | — | — |
| song140 | 7.35x / 212px | **4.75x / 274px** | 2.50x / 370px |

뷰포트 반높이가 360px 라 ±8 부터는 행성이 화면 밖으로 나간다. 그래서 ±5 가 상한이고,
그 상태에서도 4.75x 다.

**근본 해결은 카메라가 아니라 twirl 이다.** 실제 얼불춤 채보가 타일의 25% 에
twirl(회전방향 반전)을 거는 게 정확히 이것 때문이다 — twirl 이 있어야 연속 8분음이
원이 아니라 지그재그가 된다. 아직 미구현.

## 오토플레이 데모와 자동 보정 (2026-08-11)

실사용에서 사고가 셋 겹쳐 드러났다(스크린샷 증거):

1. **판정이 평균 +79.7ms 늦게 읽히는데 오프셋 슬라이더가 +150 에서 끝났다.**
   블루투스 이어폰은 150~250ms 가 예사다 — 실제 지연 ~230ms 는 보정 범위 밖이었다.
   슬라이더를 -250~+400 으로 넓히고, 결과 화면 **A** 로 이번 판의 평균 오차를
   오프셋에 그대로 얹는다(표본 4개·평균 10ms 이상일 때만 제안). 평균 +80 인
   사람에게 슬라이더를 손으로 더듬게 하는 건 캘리브레이션이 아니라 고문이다.
2. **리플레이가 신기록을 덮어썼다.** 미스투성이 리플레이 실패가 '진행 신기록'에
   올라간 사고. 기록·리플레이 저장 전부에 `not _replay_mode and not _auto_mode`
   가드 — '본 것'이 '친 것'을 덮어쓰면 안 된다.
3. **"오토플레이는 항상 정확해야 한다."** V(리플레이)는 내 플레이의 충실한
   재현이라 내가 못 치면 리플레이도 못 친다 — 그건 기능이지 버그가 아니다.
   대신 **O** 가 진짜 오토플레이 데모다: 봇이 전 타일을 delta 정확히 0 으로
   밟는다(홀드 밟기-떼기 포함). 사람 입력 경로의 프레임 오차조차 안 태우려고
   리플레이와 같은 통로(_apply_press)에 0 을 직접 먹인다.
   AutoScene 테스트가 '전 delta == 0 · P 100%' 를 잠근다.

## 난이도·레이팅·배지 — adofai.gg 흡수 (2026-08-11)

adofai.gg(얼불춤 커뮤니티 레벨 DB)에서 세 가지를 차용했다.

**난이도 등급 (1~21 스케일 + 색 램프)** — adofai.gg 는 신뢰 큐레이터가
매기지만 우리는 곡 전부가 파이프라인 산출물이라 잰 숫자로 매긴다
(`make_charts.difficulty_of`, 채보에 `difficulty` 로 저장):

- **속도** = 피크 탭속(2초 창 95백분위 — 최댓값은 한 번의 버스트에 휘둘린다)
  0.9 + 평균 탭속 0.75. 처음엔 로그 혼합이었는데 14곡이 11.1~13.0 으로
  뭉쳐 변별이 없었다 — 선형으로 바꿔 8.5~11.2 로 퍼졌다.
- **압박** = 연속 간격 130ms 미만 비율 x3.2 (한계 근접 구간의 길이).
- **기술** = 중간회전·트월 밀도 + 토끼 구간 + 홀드 (각 상한 있음).

보정 기준: 클릭 트랙(t01~) 1.0~3.8 · 데모 7.5 · mureka 8.5~11.2.
절대 척도가 아니라 '우리 목록 안의 서열'이 목적이다. 곡 선택 목록의
난이도 숫자는 adofai.gg 색 램프(하늘→초록→노랑→주황→빨강→보라)를 따른다.

**플레이 레이팅** — `난이도^1.6 x ((정확도-70)/30)^2`. 어려운 곡이
지수적으로 크고, 고정확 구간이 가파르다(100%: x1 · 95%: x0.69 · 90%: x0.44).
실패는 0. **종합 레이팅**은 곡별 최고 레이팅의 내림차순 0.9^i 감쇠 합
(osu/adofai.gg 방식) — 한 곡을 갈아서 올리는 데 상한이 있고 여러 곡을
도는 게 유리하다. 곡 선택 상단에 표시.

**클리어 배지** — **PP**(전 판정 PERFECT) > **FC**(미스 0). 랭크와 축이
다르다: E/L 섞인 노미스는 'FC 인데 A랭크', 미스 낀 고정확은 'S 인데 배지
없음'이 된다. 체크포인트를 썼으면 배지 없음 — 부활로 이어붙인 노미스는
노미스가 아니다. 기록엔 최고 배지만 남는다(PP 가 FC 를 덮는다).

## 판정창 조이기 — "다 쉽다"의 절반은 판정이었다 (2026-08-10)

채보 밀도를 원작 엑스트라급(체감 BPM p95 364~556)까지 올렸는데도 쉬웠다.
미스 창이 ±110ms 라 100ms 어긋나도 안 죽었기 때문이다. 계측도 끝났다 —
실측 사람 산포 σ 20~30ms 에서 Perfect ±30 은 절반쯤 운이었다.

기준창 110/60/30 → **80/45/25**. 판정창-이웃 캡(`set_gaps`)은 그대로라
빠른 구간은 여전히 자동으로 더 좁아진다. 창 값에 묶인 테스트 셋을
같이 재조준했다(경계가 아니라 '띠의 중앙'을 겨냥한다 — 프레임 히치 여유).

## 리플레이 — 손맛 디버깅의 되감기 (2026-08-10)

이 프로젝트의 목표가 "손맛을 평가할 수 있다"인데, 산포가 어디서 무너졌는지는
숫자만으로 안 보인다. 결과 화면에서 **V** 로 방금 판을 다시 본다.

핵심 설계: **키 입력이 아니라 '판정 결과'를 기록한다** — (종류, 타일, delta).
재생은 기록된 delta 를 그대로 재판정하므로 점수·등급·산포가 **비트 단위로
재현**된다(ReplayScene 테스트가 원소 단위로 잠근다). 프레임 양자화로 발화가
몇 ms 밀려도 판정이 안 흔들리는 이유다. 미스와 체크포인트 부활은 기록하지
않는다 — 같은 판정 열이면 감시자와 체력이 같은 자리에서 알아서 재현하고,
부활의 클럭 되감기도 순차 재생이 자연히 견딘다(발화 조건이 '클럭 >= 목표'라
되감기면 다음 이벤트가 그냥 기다린다).

실입력과 리플레이는 `_apply_press` 한 경로를 탄다 — 갈라두면 언젠가 한쪽만
고쳐져 리플레이가 거짓말을 한다. 실플레이만 디스크에 남는다
(`user://replays/`) — 테스트 러너는 사용자 파일을 오염시키지 않는다는
규약 그대로. HUD 에 REPLAY 표식, R 로 리플레이를 끊고 직접 칠 수 있다.

## 경로를 낱개 타일로 그린다

원래 `Line2D` 연속 획이었다. 타일로 바꾼 건 장식이 아니라 **조작 편의** 때문이다.

연속선은 다음에 어디서 밟는지를 눈으로 셀 수 없다. 타일이 나뉘어 있으면
**남은 개수가 그대로 남은 박자 수**라서 타이밍을 눈으로 준비할 수 있다.
원작이 타일로 그리는 이유가 이것이다.

각 타일은 한 변이 간격과 같은 정사각형이고 그 타일에서 나갈 방향으로 회전한다.
직선 구간에서는 중심 간격 == 한 변이라 정확히 맞닿는다. 꺾이는 데선 안쪽이 겹치고
바깥이 벌어지는데 원작도 같은 모양이다.

**타일은 채우기가 아니라 윤곽선으로 읽힌다.** 안은 거의 비어 있고(alpha 0.10~0.22)
테두리만 밝다. 테두리 색 성분을 1.0 넘게 주면(HDR) `WorldEnvironment` 글로우가 걸려서
선이 발광한다. 채우기를 불투명하게 하면 경로가 벽처럼 보여서 그 느낌이 안 난다.

상태별로 다르게 칠한다 — 이게 있어야 '지금 밟아야 할 타일'이 눈에 들어온다:

| 상태 | 채우기 | 테두리 |
|---|---|---|
| 지나감 | 0.10 alpha | 어둡게 (0.35, 0.42, 0.62) |
| 앞으로 올 것 | 0.14 alpha | HDR (1.15, 1.35, 1.90) |
| **지금 목표** | 0.22 alpha | **HDR (2.20, 2.00, 1.10)** · 굵기 3.5 |

### 타일 모양은 '나갈 방향' 하나로 정하면 안 된다 (2026-08-10)

타일 종류(고스트·중간회전·홀드·체크포인트)를 아무리 늘려도 화면은 계속
'사각형 무더기'로 보였다. 밑바탕 모양이 전부 같았기 때문이다.

**원인 1 — 모양이 나갈 방향만 봤다.** `_quad(center, deg, half)` 가 정사각형을
`angles[i]` 로 돌리기만 했다. 그래서 꺾이는 자리에서 앞 타일의 끝변과 이 타일의
앞변이 서로 다른 각도라 어긋나고, 안쪽은 겹치고 바깥쪽은 벌어졌다.

원작처럼 **두 방향에서** 만든다:

```
앞변 ⊥ 들어온 방향 (angles[i-1])   ·   끝변 ⊥ 나갈 방향 (angles[i])
```

그러면 이웃과 변이 정확히 맞물린다 — 수학적으로는. **이 결론은 하루 만에
뒤집혔다.** 실전에서 쐐기 기하는 불안정했다: 꺾임각에 따라 타일 넓이가
요동치고(90도 코너는 절반 넓이), 중간회전이 낀 각도 조합에서 사변형이
자기 자신과 교차해 **나비넥타이**로 렌더됐다(실측 스크린샷: 목표 타일이
접힌 슬리버). 마커 크기 보정까지 얹어야 했다.

②번 시도(고정 사각형 + 이등분선 회전)는 안정적이었지만 꺾이는 자리마다
이웃끼리 대각선으로 겹쳐 '카드 무더기'로 보였다. 원작 스크린샷과 나란히 놓고
보면 원작 타일은 **이음매에서 만나 하나의 띠로 이어진다**.

최종(③): 타일 i 는 **굽은 도미노**다 —
앞 이음매(이전 타일과의 중간, 들어온 방향에 수직)에서 출발해 중심에서 꺾이고
뒤 이음매(다음 타일과의 중간)에서 끝난다. 팔꿈치 점은 폴리라인 미터 조인
공식 그대로: `M = ±(v_in+v_out)·half / (1+u_in·u_out)`, 상한 1.6half 로 잘라
급한 꺾임의 스파이크를 막는다(잘린 자리는 둥글림이 다듬는다).

- 직선 = 정확히 맞닿는 직사각형(이음매 = 두 중심의 중점이므로 자명하다)
- 꺾임 = 팔꿈치 · U턴 = 직사각형 폴백(폭이 0 이 되는 자리)
- 폭·길이가 상수라 ①의 불안정이 없고, 이음매가 맞물려 ②의 겹침이 없다

종류별 실루엣(마름모·길쭉함)은 접었다 — 트랙 연속성을 깨기 때문이다.
종류는 마커(색·모양)가 말한다. 고스트만 작게 유지한다(밟지 않는 길이라
끊겨 보이는 게 오히려 맞다).

U턴은 앞변과 끝변이 같은 자리로 겹쳐 모양이 사라진다. 경로가 실제로 되돌아가는
자리라 겹치는 게 맞지만 안 보이면 안 되므로 정사각형으로 둔다(`_FOLD_DOT`).
접힘 판정은 **늘림을 곱하기 전 단위벡터로** 해야 한다 — 아니면 임계가 흔들린다.

**원인 3 — 각져 있었다.** 위까지 하고 보니 90도 코너가 완전한 삼각형이라
뾰족하게 튀었다. 원작 타일을 확대해 보면 각진 사각형이 아니라 **모서리가 둥근
캡슐**이고, 끝이 노출된 자리는 반원으로 마감된다. 둥근 끝이 이웃과의 각도 차이를
흡수하기 때문에 **어떤 각으로 꺾여도 이음매가 매끄럽다** — 각진 도형이
미터 이음을 정확히 맞춰야만 얻던 걸 공짜로 얻는다.

`_round_poly` 가 꼭짓점마다 2차 베지에로 굽힌다(제어점 = 원래 꼭짓점).
반지름은 `min(r, 붙은 두 변 중 짧은 쪽 / 2)` 로 자른다 — 90도 코너처럼
한 변이 0 인 자리에서 안 자르면 도형이 뒤집힌다. 겹친 꼭짓점은 먼저 지운다.

비용: 타일당 점이 4개 -> 20개. `TilePath` 는 커서가 바뀔 때만 다시 그리므로
매 프레임 부담이 아니다 — 848타일 채보 자동플레이에서 137fps(이전 145fps).

**따라오는 문제 — 마커가 타일 밖으로 나갔다.** 모양은 종류마다 달라졌는데
마커(소용돌이·겹고리·마름모·고리)는 여전히 '타일 좌표에 고정 크기'로 그리고 있었다.
좁은 쐐기에서 표시가 도형 밖으로 삐져나가 **잘린 것처럼** 보였다 —
실측 mureka_08 의 중간회전 타일 345개 중 **94개**가 최대 18px 넘어갔다.

두 값을 도형에서 가져와 고쳤다(`_marker_fit`):

| | 왜 |
|---|---|
| 자리 = 면적 가중 **무게중심** | 쐐기는 타일 좌표가 도형 중심이 아니다 |
| 크기 = 그 점에서 변까지 최단거리(**내접원**) / half | 좁으면 알아서 줄어든다 |

정사각형이면 무게중심 = 원점이고 내접반경 = half 라 배율이 정확히 1.0 —
**예전 채보는 한 픽셀도 안 바뀐다**. 적용 후 삐져나감 94개 -> **0개**.
너무 줄면 무슨 표시인지 못 읽으므로 `MARKER_MIN_SCALE = 0.5` 로 바닥을 둔다.

낙하 중에는 타일이 줄어드는데 마커가 안 줄어 허공에 뜬 것처럼 보였다 —
같은 비율을 넘겨 같이 줄인다.

**원인 2 — 종류가 마커로만 표시됐다.** 소용돌이·마름모·고리를 얹어도 밑바탕이
같으면 경로를 훑을 때 '무슨 타일인지'가 아니라 '마커가 붙었나'만 보인다.
모양 자체가 기능을 말하게 했다:

| 타일 | 실루엣 | 왜 |
|---|---|---|
| 일반 | 사각형 (꺾이면 쐐기) | — |
| 고스트 | 작은 사각형 + 점선 | 안 밟는다 |
| 체크포인트 | **마름모** (45도) | 랜드마크 — 맞물림을 포기하고 눈에 띄는 쪽 |
| 홀드 | **진행 방향으로 길쭉** (바퀴에 비례, 상한 2.2배) | 시간을 더 차지한다는 걸 길이로 |

늘림은 **길이만** 늘려야 한다. 늘인 벡터에서 수직을 뽑으면 타일이 같이
뚱뚱해진다 — 방향과 크기를 분리해서 수직 성분을 먼저 뽑아 둔다.

낙하·임팩트도 같은 모양을 쓴다(`_quad_of` 가 로컬 모양을 회전·확대해 옮긴다).
안 그러면 밟는 순간 타일이 사각형으로 바뀌어 튄다.

### 타일 임팩트

밟은 타일이 **판정 색으로 부풀면서 사라진다**(0.22초). 방사 플레어도 같이 터진다.
커졌다 돌아오는 게 아니라 커지면서 사라져서 잔상처럼 읽힌다.

색이 곧 판정이다: Perfect 초록 · E/L Perfect 연두 · Very 노랑 · Miss 빨강.
어느 타일을 어떻게 밟았는지가 경로 위에 남아서, 다음 구간을 준비하면서도
직전 결과를 읽을 수 있다.

임팩트는 순수 연출이라 오디오 클럭이 아니라 프레임 시간으로 감쇠시킨다
(화면 흔들림과 같은 취급). 활성 임팩트가 없으면 `set_process(false)` 로 멈춘다 —
174개 타일을 이유 없이 매 프레임 다시 그리지 않는다.

## 화면 요소

### 중앙 상단 — 판정 + 콤보

시선이 경로를 따라 움직이므로 판정을 타일 옆에만 띄우면 놓친다.
**화면에 고정된 자리가 하나 필요하다.** 판정 이름과 콤보 숫자를 판정 색으로 띄운다.

### 시작 카운트다운

인트로가 16박이라 전부 세면 지루하다. **첫 타일까지 4박 남았을 때부터** 센다
(`Main.COUNTDOWN_BEATS`). 박자마다 밝기가 살아나고 마지막에 `GO`.

### 왼쪽 — 타건 키뷰어 (2026-08-11)

얼불춤 커뮤니티 KeyViewer 모드의 우리 판. 판정키 타일이 누르면 켜지고,
키별 누적 타수와 **최근 1초 KPS** 를 같이 보여준다 — 양손 교타에서 어느
손이 노는지, 순간 몇 타까지 올라가는지가 손맛 계측의 일부다.

- 기본 바인딩(비어 있음 = 전부 판정키)에선 **처음 눌린 순서로 슬롯 생성**
  (최대 8). K 바인딩을 했으면 그 키들을 처음부터 고정 배치.
- 데이터는 스스로 줍지 않고 Main 이 먹인다: 실입력은 판정키 필터 통과분만
  (ESC·R 이 깜빡이면 잡음), 리플레이·오토는 키 이벤트가 없어
  `_apply_press` 가 유일한 소스다(탭 플래시 110ms, 홀드는 sustain 승격).

### 배경 — 비트 동기 셰이더 (2026-08-11)

`shaders/background.gdshader`. 에셋 0개 원칙 그대로 — 노이즈 텍스처 없이
사인 3겹 드리프트 + 정박 지수감쇠 고동 + Perfect 여운 + 비네트.

- **위상은 항상 AudioClock 에서 파생**한다. 배경이 스스로 시간을 세면
  일시정지·시크에서 음악과 어긋난 채 혼자 고동쳐 박자를 방해한다.
- 틴트 = 곡 난이도 색(SongSelect 램프 공유) · 에너지 = 콤보.
- 첫 튜닝은 "너무 번쩍거린다" — Perfect 마다 flash=1.0 리셋이 초당 5탭
  구간에서 스트로브가 됐다. maxf(0.5) 상한 + 가중 절반으로 눌렀다.
  고동은 배경의 숨이지 조명이 아니다.

### 설정 창 — 곡 선택 S 키 (2026-08-11)

↑↓ 항목 · ←→ 조절 · Enter/ESC 저장 후 닫기. 전부 `records.json`에 남는다.

| 항목 | 값 | 비고 |
|---|---|---|
| 판정 엄격도 | 관대 x1.4(미스 ±112ms) / 보통 x1.0(±80) / 엄격 x0.7(±56) | 얼불춤 판정 난이도 차용. 이웃-간격 캡은 배율 무관 — 관대여도 겹친 판정창은 안 된다 |
| 음악 볼륨 | 0~100% | AudioClock 플레이어. 카운트인 틱도 음악에 구워져 있어 함께 조절된다 |
| 효과음 볼륨 | 0~100% | hit/miss. 기본 -4dB 트림 위에 얹힌다 |
| 입력 오프셋 | -250~+400ms | 인게임 슬라이더와 같은 저장소. 결과 화면 A = 자동 보정 |

판정 엄격도는 세 지점에서 드러난다: **시작 카운트인 아래**(또렷하게, 시작
전 체크) → **플레이 중**(보통은 숨고 관대=초록/엄격=빨강만 흐리게 잔류) →
**결과 화면**("판정 관대 (창 x1.4)"). 배율이 걸린 채 기록을 가는 걸
본인이 모르는 상태가 없어야 한다. 적용은 실플레이만 — 러너가 사용자
설정에 좌우되면 기계마다 다르게 죽는다.

### 완주 결과 화면

랭크 · 정확도 · 판정 분포(너무 빠름 / 빠름 / 빠름! / 정확 / 느림! / 느림 / 너무 느림) ·
최대 콤보 · **판정 오차 평균과 표준편차**.

마지막 두 개가 중요하다: 평균이 치우쳤으면 오프셋 슬라이더로 고칠 수 있고,
표준편차가 크면 못 고친다. 결과 화면이 그 구분을 매번 보여준다.

정확도별 문구: 100% 완벽한 플레이 · 99%+ 거의 완벽 · 95%+ 훌륭한 클리어 ·
90%+ 클리어 · 70%+ 완주 · 그 아래 다시 해보자.

### 실패 조건 — 체력 (정확도 기반에서 교체)

처음엔 "정확도 55% 아래면 실패"로 만들었는데 실사용에서 바로 깨졌다:

- 정확도는 **누적값**이라 한 번 떨어지면 회복이 사실상 불가능하다.
  초반에 감 잡느라 몇 개 놓치면 그걸로 끝 — 리듬게임에서 그건 가혹하다.
- 안 치고 **보고만 있어도** 12판정 만에 실패했다(1분 9초 곡이 11초에 종료).

그래서 표준 해법인 **체력**으로 바꿨다(`Score.health`):

| 이벤트 | 체력 변화 |
|---|---|
| 미스 (TooEarly/TooLate) | **−7** |
| Perfect | +1.6 |
| E/L Perfect | +1.0 |
| Very Early/Late | +0.4 |

- 시작 100. 0이 되면 실패. 연속 미스 기준 **약 15개**에 죽는다.
- 잘 치면 돌아온다 — 나쁜 출발이 사형선고가 아니다.
- **한 번도 안 눌렀으면 아예 깎지 않는다**(`Score.started`). 보고 있는 건 실패가 아니다.
- 화면 상단 중앙에 체력 바. 60 아래 노랑, 30 아래 빨강.

스모크 실측: 무입력 → 무피해 완주 · 20% 미스 → 체력 78 생존(랭크 B) ·
50% 미스 → 39타일에서 체력 0 사망.

### 정지 후 클럭

정지하면 `get_playback_position()` 이 **0** 을 돌려준다. 그대로 계산하면 클럭이
곡 길이만큼 통째로 뒤로 간다(실측 −20.9초). `now_ms()` 는 정지 상태에서
마지막 값을 유지한다.

### 카메라 가드는 '스파이크 비율'로 잰다

"한 프레임 최대 이동 < 20px" 가드는 틀린 지표였다 — 같은 코드로 4회 돌려
최대값이 5.2 / 10.0 / 17.5 / 36.3px 로 흩어졌다(p99 는 3.0~3.3px 로 일관).
그건 카메라 설계가 아니라 **OS 프레임 히치**를 재는 값이다.
진짜 불연속은 여러 프레임에 걸쳐 나타나므로, 중앙값의 8배를 넘는 프레임의
**비율**(> 0.3% 면 실패)로 본다.

### 지나간 타일이 떨어져 나간다

원작의 `trackDisappearAnimation`. 밟고 지나간 타일이 중력으로 떨어지며 회전하고
1.15초에 걸쳐 사라진다. 다 떨어진 타일은 아예 안 그린다.

난수(초기 속도·각속도)는 **떨어지기 시작할 때 한 번만 뽑아 저장한다.**
매 프레임 뽑으면 타일이 제자리에서 부들거린다.

한 프레임에 여러 칸 전진할 수도 있으므로(랙 스파이크) `set_cursor` 가
직전 커서부터 새 커서까지 전부 떨어뜨린다.

## MIDI → 곡 + 채보 (AI 음악 경로)

> **주의 — mureka_* 채보는 이 저장소만으로는 재생성되지 않는다.**
> `.gitignore` 원칙은 '생성 자산은 생성기로 언제든 재생성된다'인데, mureka 채보만
> 이걸 어긴다. 원본이 Mureka 에서 받은 스템 MIDI 라 저장소에 없기 때문이다.
> `.tres` 는 커밋되고 `.wav` 는 ignore 되므로, 다른 머신에서 클론하면 14곡이
> 전부 아래처럼 죽는다(게임은 살아 있고 목록에서 조용히 빠진다):
>
> ```
> ERROR: Resource file not found: res://assets/mureka_03.wav
> ERROR: res://charts/mureka_03.tres:11 - Parse Error: [ext_resource] ...
> ```
>
> 내장 채보(t01~t05·demo·song140·test_song)는 `make_charts.py` · `make_song.py` ·
> `make_click.py` · `make_test_midi.py` 로 전부 재생성되므로 영향이 없다.
> 정리하려면 둘 중 하나다 — **원본 MIDI 를 저장소에 넣거나**(86파일 740KB,
> WAV 하나보다 작다), **mureka 채보를 ignore 로 빼거나**. 지금은 한 머신에서만
> 쓰므로 그대로 두었다.


```bash
python3 tools/make_test_midi.py                 # 검증용 픽스처 생성
python3 tools/midi2song.py assets/test_song.mid # MIDI -> wav + json + .tres
godot --headless --script res://tests/verify_chart.gd -- --chart=res://charts/test_song.tres
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn -- --autoplay --chart=res://charts/test_song.tres
```

AI(AIVA·Suno Studio 등)에서 **MIDI 를 받아오면** 이 한 줄로 곡과 채보가 나온다.
AI 오디오를 직접 받지 않는 이유(2026-08 조사): 생성 오디오는 전부 미세 템포
드리프트가 있고(0.5% 면 3분에 ~900ms), 온셋 검출(madmom)은 120bpm 초과에서
정확도 11% 로 붕괴한다. **MIDI 틱은 이미 박자 도메인**(tick/PPQ = 박)이라
드리프트 0 · 온셋 검출 불필요 — AI 에겐 작곡만 시키고 오디오는 우리가
샘플 단위 정확하게 렌더한다.

변환기가 게임 제약을 전부 강제한다(각각 로그를 남긴다):

| 함정 | 처리 |
|---|---|
| 그리드 벗어난 노트 | 1/12 박 격자로 양자화 + 최대 오차 보고 |
| 코드(동시 노트) | 온셋 1개로 합침 |
| 카운트인 없음 | 전체 +N박 시프트 (오디오·템포·온셋을 같이 민다) |
| **MIDI 템포 변경** | **토끼/달팽이 타일로 변환.** 게임은 홉당 상수 배속이라 변경 지점에 타일이 필수 — 없으면 강제 삽입 |
| **한 성부만 따라가서 심심함** | **반주 층으로 밀도 보강** (아래) |
| **전사 잡음으로 붙어버린 온셋** | 100ms 미만 간격은 뒤 타일을 버린다 (`--floor-ms`) |
| 2박 초과 공백 | 걸음 채움 타일 — 공백을 **등분**한다 (한 타일 최대 대기 = 2박, `--no-fill` 로 에러 처리 가능) |
| 멜로디 트랙 판별 | '나올 채보'의 점수(덮음 · 촘촘 · 밀도)로 선택 (`--melody-track N` 으로 지정) |

### 밀도 보강 — 채보가 심심했던 진짜 이유 (2026-08-07)

곡을 여럿 넣고 나서 "타일 수가 너무 적다"는 게 눈에 띄었다. 재보니 실제로 그랬다:

| | 초당 탭 | 2박 걸음 채움 비율 | 800ms 넘는 공백 |
|---|---|---|---|
| mureka_07 | **1.43** | **67%** | 177개 |
| mureka_neon | 1.54 | 52% | 118개 |
| 14곡 평균 | 2.0 | 33% | — |

**멜로디 한 성부만 채보로 썼기 때문이다.** 그 성부가 쉬면 채보도 쉰다.
mureka_07 은 멜로디 온셋이 96개뿐이라 곡의 2/3을 '음악에 없는 자리'를
841ms 마다 한 번씩 밟고 있었다. 심심한 채보가 아니라 **빈 채보**였다.

얼불춤 창작마당 채보는 한 성부를 따라가지 않는다. 보컬이 쉬면 드럼을,
드럼이 빠지면 신스를 밟는다 — 지금 들리는 것 위에 타일이 있다.
그래서 공백을 메트로놈 걸음이 아니라 **실제 반주 온셋**으로 채운다.

층은 리듬적 현저성 순이고, 위 층으로 공백이 메워지면 아래 층은 안 쓴다:

```
드럼 백비트(킥·스네어) → 베이스 → 그 외 성부 → 하이햇 → (진짜 무음이면) 걸음 타일
```

**단위가 둘로 나뉘는 게 핵심이다.**

- **천장 = 박** (`--fill-above-beats`, 기본 1.0). 심심함은 음악적 개념이다.
  채보를 짜는 사람은 "한 박 넘게 비면 뭐라도 밟게 한다"고 생각하지
  "340ms 넘으면"이라고 생각하지 않는다. 박으로 두면 느린 곡·빠른 곡이
  알아서 같은 음악적 밀도가 된다.
- **바닥 = ms** (`--min-gap-ms`, 기본 150). 못 치는 건 물리적 개념이다.
  손가락과 판정창은 BPM 을 모른다.

바닥 값은 실측으로 골랐다. 150ms 면 보강이 만드는 '촘촘한 자리(<150ms)'
개수가 **멜로디가 원래 갖고 있던 개수와 같아진다** — 밀도는 두 배가 되는데
난이도의 하한은 안 건드린다. 130 으로 낮추면 그게 3~5배로 튄다
(mureka_09: 64 → 296개).

결과 (14곡): **초당 2.0 → 3.56탭**, 타일 4,313 → 8,166개, 걸음 채움 1,502 → 228개,
못 치는 타일 116개 제거, 최소 간격의 최저값 17ms → 105ms.

**성긴 곡은 겹침도 같이 줄었다.** 2박 홉은 기하적으로 항상 U턴이라
경로 겹침의 주범인데(위 '경로 계획' 참조), 그게 실제 온셋으로 쪼개지면서
0.25~0.75박 홉이 됐다. mureka_07 은 겹침이 21 → 7쌍이 됐다.

**대신 촘촘한 곡은 겹침이 늘었다 — 이건 기하학적으로 당연하다.**
홉이 짧을수록 꺾임이 커진다(0.25박 = 135도). 밀도를 올리면 짧은 홉이 늘고,
짧은 홉이 이어지면 경로가 코일이 된다. 플래너로도 못 편다 — 각도를 정하는 건
리듬이기 때문이다.

| | 간격 중앙 | 겹침 |
|---|---|---|
| mureka_09 | 271ms | 5쌍 |
| mureka_07 | 280ms | 7쌍 |
| mureka_14 | 173ms | 269쌍 |
| mureka_06 | 219ms | 372쌍 |

원작의 고속 구간이 꽃/나선 모양으로 뭉치는 것과 같은 현상이라 그 자체가
틀린 건 아니다. 다만 **밀도와 경로 가독성은 맞바꾸는 관계**라는 걸
기록해 둔다 — 더 조이려면 밀도(`--fill-above-beats`)를 곡별로 낮추는 게
플래너를 손보는 것보다 확실하다.

#### 못 치는 간격 정리 (`--floor-ms`, 기본 100)

밀도를 올리고 나서 로그를 보니 **최소 간격이 17ms** 인 곳이 있었다.
보강이 만든 게 아니다(바닥이 150ms 다) — 전사 멜로디가 원래 갖고 있던 것이다.
1/12박 간격으로 붙은 온셋 쌍이 300~375bpm 구간에 놓이면 17~33ms 가 된다.
판정창은 이웃까지 거리의 45%로 눌리므로(`Judge.set_gaps`) 17ms 면 창이 ±7ms —
둘 다 치는 건 불가능하고 뒤엣것은 **확정 미스**다. 난이도가 아니라 결함이다.

그래서 마지막에 한 번 훑어서 100ms 미만 간격을 없앤다(뒤 타일을 버린다).

**바닥이 두 개인 게 맞다.** `--min-gap-ms`(150)는 *우리가 새로 놓아도 되는*
최소 간격이라 보수적이어야 하고, `--floor-ms`(100)는 *곡에 원래 있어도
참아주는* 최소 간격이라 관대해야 한다. 하나로 합치면 빠른 구간이 통째로 지워진다.

**속도 타일은 절대 안 버린다.** 그 타일이 없으면 그 구간의 배속이 통째로
틀리기 때문이다 — 대신 그 옆엣것을 버린다. 보호 목록은 '새로 삽입한 것'이
아니라 **템포 맵의 모든 변경점**이어야 한다. 원래 노트와 자리가 겹쳤던
변경점은 삽입 목록에 없어서, 그것만 넘기면 정리 단계가 지워버리고
'속도 변경은 타일 위에' 불변식이 깨진다.

실측(mureka_14): 최소 간격 29ms → 115ms, 120ms 미만 자리 104개 → 13개.
남은 13개는 멜로디와 속도 타일이 직접 부딪히는 자리라 어느 쪽도 못 버린다.

#### 같이 잡힌 두 버그

1. **걸음 채움이 못 치는 자리를 만들었다.** 2박씩 그리디로 놓아서
   (`a+2, a+4, …`) 2와 1/12박짜리 공백에선 마지막 조각이 1/12박만 남는다 —
   172bpm 이면 **29ms**. 등분으로 바꿨다(두 조각 다 1과 1/24박). 계산도 박(float)이
   아니라 격자 '칸' 정수로 한다 — 반올림이 마지막 조각을 2박 너머로 밀 수 있었다.
2. **속도 타일이 보강 타일 옆에 끼어들었다.** 속도 타일은 위치를 못 옮기지만
   (옮기면 그 구간 배속이 통째로 틀린다) 보강 타일은 안 놓으면 그만이다.
   그래서 **속도 타일 삽입을 밀도 보강보다 먼저** 한다. 순서가 반대였을 때
   35ms 간격이 15개 생겼고, 바꾸니 최소 간격이 105ms 가 됐다.

### 음색 — "원곡처럼 안 들린다" (2026-08-10)

곡은 정상 재생되는데 노래로 안 들렸다. 원인은 합성기였고, 재보니 세 가지가 겹쳐 있었다.

| | 이전 | 이후 |
|---|---|---|
| 기본주파수 정수배 '밖'으로 새는 에너지 (A6) | 2.87% | **0.000%** |
| 곡 전체 스펙트럼 중심 | 10,199 Hz | **4,402 Hz** |
| 12kHz 초과 에너지 비중 | 44.7% | **11.8%** |

**1. 나이브 사각파의 접힘.** `1.0 if ph < duty else -1.0` 은 하모닉이 무한대까지
있어서 24kHz 위 성분이 전부 아래로 접혀 들어온다. 접힌 성분은 기본주파수의
정수배가 아니라 화음에 안 녹고 '지직'거린다. 옥타브마다 배로 늘어 A3 0.36% →
A6 2.87% 였다. → **밴드리미티드 웨이브테이블**(`tools/synth.py`). 나이퀴스트
아래 하모닉만 미리 더해 표로 굽는다. 하모닉 수를 2의 거듭제곱으로 버킷팅해
9개만 구우면 되고(밉맵), 런타임은 표 읽기라 오히려 더 빠르다 — 곡당 22초.

**2. 엔벌로프가 평평했다.** 어택 5ms 뒤 릴리스 전까지 진폭 1.0 고정. 악기가
뭐든 오르간처럼 '웅' 하고 버텼다. → **역할별 ADSR**. 실측 포락선(220Hz·0.5초):

| 역할 | 5ms | 200ms | 450ms | 성격 |
|---|---|---|---|---|
| lead | 0.84 | 0.55 | 0.41 | 뜯고 버틴다 |
| bass | 0.99 | 0.82 | 0.82 | 버틴다 |
| pluck | 0.95 | 0.31 | 0.08 | 뜯고 사라진다 |
| pad | 0.42 | 0.55 | 0.31 | 천천히 든다 |

**3. 드럼이 흰 노이즈라 히스였다.** 흰 노이즈는 Hz 당 에너지가 균일해서
최상위 한 옥타브(12~24kHz)에만 전체의 절반이 실린다. 실측 중심이 햇 15.2kHz ·
스네어 11.9kHz 였다. 1극(6dB/oct)으로는 못 잡는다 — 11kHz 에서 잘라도 12.5kHz
까지밖에 안 내려갔다. **3극(18dB/oct) 대역통과**로 햇 8.0kHz · 스네어 5.6kHz.

하모닉 상한이 음색 손잡이도 된다 — 베이스를 16하모닉으로 자르면 런타임 필터
없이 둥글어진다. 8.8M 샘플에 필터를 거는 것보다 공짜에 가깝다.

상수는 귀가 아니라 숫자로 골랐고, 그 숫자를 다시 찍어 볼 수 있다:

```bash
python3 tools/synth.py    # 스펙트럼 중심 · 피크 · 접힘 자가측정
```

### 원곡 오디오 채택 (`--audio`) — 신스가 아니라 진짜 노래를 튼다 (2026-08-10)

음색을 아무리 다듬어도 신스 렌더는 원곡의 대체가 아니라 폴백이다. 원곡 MP3 를
그대로 틀고 MIDI 는 타일 배치만 맡기는 경로를 만들었다:

```bash
python3 tools/midi2song.py ~/Downloads/midis\ \(8\)/*.mid --name mureka_09 \
    --title 과부하루프 --audio ~/Downloads/과부하\ 루프.mp3
```

위 문단(음색)의 마지막 걱정 — "정렬이 판정창을 벗어난다" — 는 재 보니 절반만
맞았다. **과부하 루프 실측(구간 6분할 상호상관)**:

| 채보가 따르는 맵 | 원곡 대비 전역 | 곡내 방황 | 잔차 σ |
|---|---|---|---|
| 원시 전사 맵 | -2.2ms | 8ms | **2.2ms** |
| dejitter 정리 맵 | -25.7ms | 48ms | 7.8ms |

**원시 전사 맵은 원곡과 사실상 같은 시간축이다.** 어긋남은 전부 dejitter 가
만든 것(자체 보고 드리프트 92.2ms). 그렇다고 원시 맵을 그대로 쓰면 템포 이벤트
501개(20ms 격자 잡음)마다 속도 타일이 박히고, 드리프트 캡을 걸어 봐도 캡 15ms
에서 세그먼트 115개다 — 잡음의 격자(20ms)가 캡보다 크기 때문이다.

해법은 `midilib.resample_tempos_at_tiles`: 템포 경계를 **타일 위에만** 두고
홉마다 시간 보존 bpm 을 적합한다. 경계=타일이라 '속도 변경은 타일 위' 불변식이
구성적으로 성립하고, **타일의 벽시계는 원시 맵과 정확히 같다**(오차 0). 남는
채보-원곡 오차는 격자 스냅분(½칸, 202bpm 에서 ≤12.3ms)뿐이다.

그 대가로 speed_changes 에 홉 단위 미세 배율(±7% 잡음, mureka_09 실측 212개)이
실리는데, 이건 기계적 보정이지 플레이어가 반응할 속도 변경이 아니다 — 그래서
표시를 분리했다: 의도된 변경(정리 맵)만 `speed_display_beats` -> `Chart.speed_display`
로 내려가 마커·HUD 에 나오고, 배속 자체는 speed_changes 가 전부 담당한다.

정렬은 가정하지 않고 잰다: 킥·스네어(hat 제외 — 8분음표로 깔려 판별력을 죽인다)
시각열을 원곡 에너지 플럭스에 상호상관해 전역 오프셋을 찾고, 6구간 국소 오프셋
산포가 게이트(σ8ms·범위25ms)를 넘으면 변환을 거부한다 — 곡-스템 짝이 틀리면
여기서 걸린다. 실측: 오프셋 +5.0ms · σ 5.4ms · 범위 14ms 로 통과, 파일 검증
0.000002ms/타일 · 엔진 검증 0.058ms · 오토플레이 스모크 랭크 P·100%·σ 2.5ms.

소스 매핑(전수 bpm 대조): **mureka_NN ↔ `~/Downloads/midis (NN-1)`** (01은
무번호). 원곡 mp3 는 Mureka 에서 곡별로 받아야 하고, 현재 mureka_09 만 원곡이다.

### 믹스 — "채보 멜로디"와 "곡의 주인공"은 다른 성부다 (2026-08-10)

음색을 고친 뒤에도 몇 곡이 잘 안 들렸다. 원인이 둘이었고, 하나는 우리 잘못이다.

**우리 잘못 — 곡의 주인공을 배경으로 깔았다.** `track_role` 이 '채보가 따라가는
성부'에게 가장 큰 소리를 줬는데, 그 둘은 같은 게 아니다:

> 채보 멜로디는 **칠 만한** 성부다 — 너무 촘촘하면 못 치니까 탈락한다.
> 곡의 주인공은 **들리는** 성부다 — 촘촘할수록 주인공인 경우가 많다.

실측 mureka_01: 채보는 베이스(노트 268개)를 따라가는데 곡을 이끄는 건
synth lead(노트 **2,487개**)다. 그런데 리드가 `pad` 로 분류돼 amp 0.14,
전체에서 제일 조용한 값이었다. mureka_03(1,638) · mureka_07(1,335) 도 같았다.

진폭을 **악기 이름**에서 정하고 채보 멜로디에는 배수(`MELODY_BOOST` 1.35)만
얹도록 바꿨다 — 플레이어가 자기가 치는 성부를 귀로 따라갈 수 있어야 하니까.

**드럼이 믹스를 먹고 있었다.** 노트 수가 압도적이라(mureka_03: 드럼 1,150 vs
베이스 126) 에너지의 55~74%가 드럼이었다. 킥 0.72→0.54 · 스네어 0.60→0.45 ·
햇 0.13→0.10.

| 앞 30초 에너지 비중 | 이전 | 이후 |
|---|---|---|
| mureka_01 드럼 / 채보멜로디 | 54% / 13% | **21% / 33%** |
| mureka_03 드럼 / 채보멜로디 | 74% / 5% | **42% / 22%** |

전곡 RMS 편차 0.7dB · 클리핑 0.

**우리 잘못이 아닌 쪽 — 전사 MIDI 에 구멍이 있다.** 렌더 무음 구간이 소스의
무음 구간과 거의 정확히 일치한다(아래). 오디오→MIDI 전사기가 놓친 부분은
우리가 만들어낼 수 없다.

| 곡 | 소스 무음 | 렌더 무음 |
|---|---|---|
| mureka_11 | 13.5% | 12.9% |
| mureka_03 | 10.4% | 11.0% |
| mureka_02 | 9.2% | 9.2% |
| 나머지 | 0~5% | 0~4% |

mureka_11 은 12\~16초 · 148\~153초처럼 **5초짜리 구멍**이 있고, 그 구간엔
5개 트랙 전부 노트가 0개다. 이 곡들은 원곡 오디오(`--audio`) 로 가는 게
유일한 해결이다 — mureka_09 가 이미 그 경로다.

### 난이도 곡선 — 서막과 클라이맥스 (2026-08-10)

밀도 보강을 곡 전체에 똑같이 걸었더니 채보가 평평했다. 실측 10초 구간별 탭/초:

```
mureka_01  평균 3.15 σ0.60   ▃▄▄▄▅▄▄▃▄▃▄▄▄▄▁      서막도 클라이맥스도 없다
```

**곡에는 기승전결이 있는데 채보가 그걸 뭉갰다.** 같은 곡의 세기 곡선은
`▃▄▅▃█▆▅▅▇▆▆▃▃▃▃` 였다. 조용한 구간은 반주로 억지로 채워 올리고, 시끄러운
구간은 이미 꽉 차서 더 못 올린 결과다.

세기(`intensity_curve`)를 재서 구간마다 **목표 탭 간격**을 바꾼다.
난이도를 지어내는 게 아니라 음악이 이미 가진 모양을 드러내는 쪽이다.

- **세기** = 온셋 밀도 0.6 + 동시에 울리는 트랙 수 0.4, 8초 창, 평활.
  둘을 섞는 이유: 온셋만 보면 드럼 롤 하나에 값이 튀고, 트랙 수만 보면
  다 같이 길게 끄는 패드 구간이 클라이맥스로 잡힌다.
- **정규화는 순위 절반 + 최소최대 절반.** 최소최대만 쓰면 세기가 한쪽에 쏠린
  곡이 통째로 서막이 된다(실측 mureka_14 3.55 -> 2.44탭/초). 순위만 쓰면
  진짜 평평한 곡에 가짜 기승전결이 생긴다.
- **목표 간격은 ms 다.** 심심함은 음악적 개념이라 박이지만(채울지 말지),
  난이도는 물리적 개념이라 ms 다 — 손과 판정창은 BPM 을 모른다.
  300ms(3.3탭/초, 서막) → 150ms(6.7탭/초, 클라이맥스).

#### 두 번 틀리고 고친 것

**1. 천장을 게이트로만 썼다.** `공백 > 천장이면 채운다` 로만 두면 '얼마나
촘촘히'를 아무도 안 정한다. 멜로디가 쉬는 구간은 공백이 몇 초씩이라 어떤
천장이든 넘고, 그러면 바닥(최소 간격)까지 꽉 채워진다 — **결과가 뒤집혀서
조용한 구간이 최대 밀도**가 됐다. 천장을 '목표 간격'으로 걸어야 서막이 서막이 된다.

**2. 탐욕 배치는 목표의 1.35배로 수렴한다.** 앞에서부터 목표만큼 띄우며 집으면,
400ms 공백에 목표 150 일 때 150 을 하나 집고 남은 250 은 바닥(115ms) 때문에
더 못 쪼갠다. 실측 목표 150ms 에 실제 201ms. **공백을 n 등분하고 각 자리에서
가장 가까운 온셋을 집는** 방식으로 바꿨다. 그 자리에 음이 없으면(목표의 70%
밖) 비워 둔다 — 없는 소리를 밟게 하지 않는다.

### 토끼는 템포가 아니라 채보 결정이다 (2026-08-10)

실측 14곡 중 13곡에 토끼가 0개였다. 속도 타일이 '전사된 템포 변경'에서만
나왔는데, 전사 템포는 dejitter 가 평평하게 만들기 때문이다. 원작의 토끼는
대부분 곡 템포가 아니라 **채보가 거는 연출**이다.

`pick_boost_sections` 가 세기 상위 구간에 x2 배속을 건다. 배속 m 은 벽시계를
보존한다 — **홉 박자 x m · 배율 x m** 이면 wall = beats·spb/mult 이 그대로다.
같은 시각에 같은 탭이고, 행성만 두 배로 돌며 스윕이 넓어진다(0.5박 꺾임이
직선이 된다). 검증 게이트가 이 항등식을 파일 단위로 잠근다.

선발 조건은 전부 기하·구조에서 나온다: 구간 안 간격 <= 1박(2배 후 최대 스윕),
홀드 없음(바퀴가 고정 2박이라 셈이 꼬인다), 8초 이상, 상한 32초(곡 절반이
토끼면 대비가 사라진다 — mureka_06 실측 90초). **처음엔 '세기 창'을 먼저 찾고
안에서 검사했는데 모든 클라이맥스에 위반이 몇 개씩 끼어 0개가 됐다** —
순서를 뒤집어 깨끗한 구간을 먼저 만들고 세기 평균으로 고른다. 결과 14곡 24구간.

### 검증 2단 — 같은 수학을 두 번 쓰지 않는다

1. **Python**: 템포 맵을 직접 적분한 '정답 벽시계' vs **생성된 .tres 파일을 읽어**
   되계산한 히트타임. 메모리의 중간값이 아니라 파일을 검증한다 — 직렬화 잘림,
   필드 누락, 타일 매핑 실수가 여기서 걸린다. (실측 오차 0.005ms)
2. **GDScript** (`tests/verify_chart.gd`): 실제 엔진의 `ChartRuntime.hit_times_ms` 가
   같은 정답을 내는지. Python 검증만으로는 '의미론을 똑같이 잘못 이해' 한 경우를
   못 잡는다 — 게임이 실제로 쓰는 코드가 최종 심판이다. (실측 오차 0.004ms)

픽스처(`make_test_midi.py`)는 실전 함정을 전부 심어둔다: 템포 변경 2회(노트 없는
지점 포함), 코드, 그리드 이탈 노트, 5박 공백, 0박 시작. 자동플레이 실측:
**랭크 P · 100% · σ 2.5ms** — 템포 변경 채보가 실제 게임플레이로 검증된다.

직렬화 정밀도 주의: `.tres` 숫자는 `%.9g` 로 쓴다. `%g`(6유효숫자)면 2/3 같은
속도 배율이 0.666667 로 잘려 긴 곡에서 히트타임이 밀린다.

### 파서는 라이터와 독립으로 검증한다

`tools/test_midilib.py` — SMF 바이트를 손으로 깎아 파서에 직접 먹인다.
파서를 자기 라이터 출력으로만 검증하면 둘이 같은 오해를 공유할 때 못 잡는다.
특히 우리 라이터는 러닝 스테이터스를 안 쓰므로, 실제 AI MIDI 가 흔히 쓰는

외부 파일 통합 확인: 위키피디아 MIDI 샘플(포맷 1 · 6트랙 · 노트 177)을

경고를 낸다.

## 정밀도와 소리 — 실곡 14개가 드러낸 것들

실곡을 넣기 전에는 안 보이던 것들이다. 픽스처 채보는 짧고 각도가 정확해서
아래 넷 다 조용히 통과한다.

### U턴은 wrap 경계 위에 얹혀 있다 (`TURN_EPS_DEG`)

U턴은 sweep 이 정확히 `0 = 360` 인 경우인데, 그 값이 `fposmod` 의 경계 그 자리다.
각도에 0.001도만 오차가 섞이면 한쪽은 `0.0006`(-> 0.0박) 다른 쪽은
`359.9994`(-> 2.0박) 가 되어 **같은 U턴이 정반대**가 된다.
`is_zero_approx`(1e-6) 로는 한쪽 끝밖에 못 잡는다.

실측: 같은 채보에서 Python(float64)은 2박, 엔진(float32)은 0박으로 갈려
히트타임이 **6.5초** 어긋났다. 각도 누적 오차는 0.0006도였다.

양쪽 끝을 다 U턴으로 본다. 여유 1.0도는 float 오차(~0.001도)보다 1000배 크고
격자의 최소 홉(15도 = 1/12박)보다 15배 작다 — 그 사이엔 정상값이 없다.
`ChartRuntime.TURN_EPS_DEG` 와 `make_charts.TURN_EPS_DEG` 가 같아야 한다.

### 히트타임 누적은 double 로 한다

`hit_times_ms` 의 반환은 `PackedFloat32Array` 다. `out[i] = out[i-1] + ...` 로
직전 값을 되읽어 더하면 **매 타일 float32 로 반올림**되고 그 오차가 무작위
보행으로 쌓인다. 200초 지점에서 float32 한 칸이 0.03ms 이므로 848타일이면
0.03 x sqrt(848) ~ 0.85ms.

실측 mureka_08 이 1.011ms 로 교차검증 허용치 1.5ms 에 붙어 있었다.
누적을 double 지역변수로 옮기자(저장은 그대로 float32) **0.0078ms** —
그 지점 float32 한 칸이다. 곡 길이와 무관해졌고 채보 15개가 전부 0.008~0.010ms
로 균일하다. `run_tests.gd` 의 900타일 누적 테스트가 이걸 잠근다
(옛 방식으로 되돌리면 2.53ms 로 즉시 FAIL).

### 곡은 피크가 아니라 라우드니스로 정규화한다

피크 정규화는 곡마다 체감 크기가 달라진다. 스템을 여러 개 합치면 가끔 우연히
정렬되는 피크 하나가 전체 게인을 정해버리기 때문이다 — 6스템 합성곡은
크레스트 18~20dB 에 RMS -19~-21dB 인데 단일 트랙 song140 은 14dB / -15dB 였다.
판정 효과음 볼륨은 song140 에 맞춰 튜닝돼 있어서, **같은 효과음이 새 곡에서만
6dB 더 튀어나왔다**.

`make_song.loudness_normalize()` 가 RMS 를 맞추고 그러다 넘치는 피크만 리미터로
누른다(블록 최대 -> 앞보기 최소 -> 릴리스 평활 -> 샘플별 보간). 앞보기 ~5ms 가
있어야 게인이 피크보다 **먼저** 내려가 트랜지언트가 안 깨진다. 블록 사이 게인
보간은 그 블록의 필요 게인으로 클램프해야 한다 — 안 그러면 천장을 넘는다.

**한 번만 걸면 목표에 못 닿는다.** 게인을 올려 맞춰도 리미터가 피크를 누르면서
RMS 가 다시 내려간다 — 실측(온셋 보강으로 밀도가 오른 뒤) 목표 -15.0dB 인데
-16.1 ~ -18.7dB 로 앉아 여유가 3.7dB 폭으로 다시 벌어졌다. 그래서 '재고 ->
모자란 만큼 더 밀고 -> 다시 리미터' 를 반복한다(`passes`). 무한정 밀지는 않는다
(`max_extra_db=6`) — 크레스트가 큰 곡을 억지로 끌어올리면 리미터가 상시 걸려
소리가 납작해지므로, 그런 곡은 조금 조용한 채로 두는 쪽이 낫다.

결과: 14곡 RMS **-15.7 ~ -15.0dB**, 효과음 여유 편차 **0.7dB**, 클리핑 0.
원곡 오디오를 쓰는 곡(`--audio`)도 같은 -15.0dB 대에 앉는다.

| 단계 | 여유 편차 |
|---|---|
| 피크 정규화(처음) | 6.0dB |
| 라우드니스 정규화 1패스 | 3.7dB |
| + 리미터 손실 반복 보상 | 1.3dB |
| + 드럼 레벨 조정(믹스 쪽) | **0.7dB** |

마지막 한 칸은 정규화가 아니라 **믹스**가 줬다. 드럼 노트 수가 압도적이라
(실측 mureka_03: 드럼 1150 vs 베이스 126) 에너지의 55~74%를 먹고 있었는데, 그걸
낮추자 피크가 덜 튀어 리미터가 덜 누르고 목표 RMS 에 더 가까이 앉는다.
**정규화로 못 메우는 건 소스에서 고치는 게 싸다.**

### 입력 효과음은 끌 수 있어야 한다 (M 키)

이 소리는 목적이 둘인데 곡에 따라 하나가 무의미해진다. 클릭 트랙에서는
'곡의 클릭과 내 입력음의 어긋남 = 내 오차' 라 캘리브레이션 도구지만, 실제
음악에서는 타일이 정의상 멜로디 온셋 위에 있어서 **효과음이 멜로디 음과 같은
샘플에 겹친다**.

그렇다고 음악에서 무조건 끌 수도 없다. 채움 타일에는 멜로디 음이 아예 없어서
끄면 그 타일은 쳐도 무음이 된다 — 실측 14곡 8166타일 중 **255개(3.1%)**, 가장
심한 곡이 8.2% 다. 그래서 기본은 켬, 곡 선택 화면에서 M 으로 토글하고
`records.json` 에 남는다.

> 이 비율은 파이프라인에 따라 크게 움직인다. 온셋 보강·`--floor-ms`·홉 분해가
> 들어오기 전에는 같은 곡들이 4838타일 중 31.3%(한 곡 69%)가 채움이었다.
> 끄기/켜기를 다시 판단할 일이 생기면 수치부터 다시 재라 —
> `filled_gap_tiles + inserted_speed_tiles` 를 `melody_onsets_beats` 로 나눈 값이다.

플레이 중(Main)이 아니라 곡 선택에 둔 이유: 바인딩이 비어 있으면 M 도 판정키다.
Main 에 두면 M 을 예약키로 뺏어야 하고 그만큼 양손 교타에서 쓸 키가 줄어든다.

## 스모크 테스트가 거짓말하던 것들

테스트가 자기 지연을 게임 탓으로 돌리면, 그 테스트는 진짜 회귀를 가린다.

### 자동플레이는 1.5프레임 늦게 눌렀다

두 가지가 겹친다 — 프레임 양자화(평균 +1/2프레임)와 `parse_input_event` 가
큐를 거쳐 **다음 프레임에 배달**되는 것(+1프레임). 145fps 면 +10.35ms.

실측이 정확히 +10.4ms 였고, 헤드리스를 32000fps 로 돌리자 **+0.3ms** 로
사라져 프레임 탓임이 확정됐다. 이 지연 때문에 촘촘한 곡에서 판정창이 좁아질 때
'자동플레이인데 정확도 95.43%' 라는 거짓 실패가 났다.

보정: 프레임 k 에서 `C_k + aD >= ht` 일 때 누르면 평균 오차가 `(1.5-a)D` 다.
a=0 -> +10.4ms · a=1 -> +3.5ms · **a=1.5 -> +0.0ms** (전부 실측).
보정 대상 곡들이 전부 랭크 P / 100.00% 가 됐다.

**앞보기에는 상한이 필요하다.** 보정이 `delta` 에 비례하므로 프레임이 한 번
크게 튀면 그만큼 일찍 눌러 멀쩡한 타일을 놓친다 — 5곡을 연달아 돌려 머신이
밀렸을 때 같은 채보가 P/100% 에서 **D/64.7%(미스 43)** 로 무너졌고 단독
실행에서는 재현되지 않았다. `MAX_LOOKAHEAD_MS`(Perfect 창 절반 아래)로 막는다 —
**판정창을 조이면 이 값도 같이 따라가야 한다.** Perfect 가 ±30 -> ±25 로 좁아졌을 때
15.0 -> 12.0 으로 내렸다. 보정이 판정창보다 크면 보정 자체가 판정을 흔든다.

정확도 판정은 **하네스가 정확히 눌렀을 때만** 한다. 입력 산포 σ 가 곧 하네스의
정밀도인데, 머신이 밀리면 벌어진다 — 실측(AV 가 새로 쓴 WAV 400MB 를 훑는 중):

| 입력 산포 σ | 정확도 |
|---|---|
| 2.3~2.9ms (조용) | 100% |
| 9.0ms | 99.42% (기준 99.0 에 아슬아슬) |
| 12.6ms | **97.69% — FAIL** |

Perfect 창이 ±25ms 로 좁아진 뒤로 σ 가 조금만 커져도 바로 떨어진다. 그 상태의
정확도는 게임이 아니라 측정 환경을 말해 주므로, σ > 5ms 면 판정을 건너뛰고
그 사실을 찍는다(`AUTOPLAY_JITTER_MS`). σ 가 정상인데 정확도가 낮으면 그건 진짜다.

미스 판정도 히치를 인정한다: 25ms 넘게 밀린 프레임을 세고 **미스가 히치 수를
넘을 때만** 실패로 친다. 0 으로 못 박으면 부하에 따라 깜빡이는 테스트가 되고,
깜빡이는 테스트는 곧 무시당한다.

### 카메라 낭비는 절대값으로 잴 수 없다

`waste > 3.0` 은 카메라의 행동과 **채보 경로의 모양**을 뒤섞고 있었다.
mureka_06 은 타일 경로 자체가 22.5x 인데 카메라가 8.5x 로 줄여 놓고도 걸렸다.
창을 ±2 에서 ±12 로 넓혀도 9.4 -> 6.0 에 그치고 행성만 402px 멀어진다 —
카메라로는 못 고치는 값이라는 뜻이다.

그래서 **감쇠비**(카메라 배수 / 타일 경로 배수)로 잰다. 기준은 **0.85** 이고,
양쪽 끝을 실측해서 잡았다:

| | 감쇠비 |
|---|---|
| 정상 (`CAMERA_WINDOW=3`) | 0.61 · 0.66 · 0.68 · **0.77**(song140, 가장 높음) |
| 회귀 (평활 제거, 창=0) | **1.00** |

**처음엔 1.0 으로 뒀다가 회귀 재현 테스트에서 그냥 통과하는 걸 보고 고쳤다.**
평활을 아예 없애면 카메라 경로가 타일 경로와 *정확히* 같아져 감쇠비가 1.00 이
된다 — 기준을 1.0 에 두면 최악의 회귀가 영원히 안 걸린다. 경계 위에 세운 판정은
판정이 아니다.

반대로 더 조이지도 말 것. 평활이 얼마나 먹히는지는 경로의 파장에 달려 있어
(창보다 긴 파장의 배회는 못 줄인다) 채보마다 정당하게 달라진다 — 0.75 로 뒀을 때
song140(0.77)이 걸렸다. 날카로운 평활 지표는 따로 있다 — 튐배수와 카메라 스파이크.

## 게임 셸

`godot` 로 실행하면 **곡 선택 화면**이 뜬다 (`SongSelect.tscn`이 메인 씬).

| 조작 | |
|---|---|
| ↑↓ + Enter | 곡 선택·시작 (마지막 선택 기억) |
| 아무 키 | 판정 — **얼불춤처럼 거의 모든 키가 판정키다.** 양손 교타가 가능해야 빠른 구간에서 손맛이 산다. R·ESC·수식키만 예약 |
| ESC | 플레이 중 일시정지 · 결과 화면에서 곡 선택 복귀 |
| R | 재시작 (일시정지 중에도) |

**히트사운드**: 키를 누른 순간 28ms 클릭이 난다. 곡의 박과 내 입력음의 어긋남이
곧 내 오차라, 화면 판정보다 빠른 캘리브레이션 도구다(얼불춤도 hitsound 가
레벨 포맷 기본 항목). `Main.tscn` 의 `HitSound.volume_db` 로 조절.

**일시정지의 정합**: `stream_paused` 는 `get_playback_position()` 을 얼린다.
언 클럭 = 시간이 안 흐름 = 감시자가 미스를 안 낸다 — 별도의 시각 저장/복원이
필요 없다. 실측: 90프레임 정지 동안 클럭 드리프트 **0.0ms**, 판정 0건
(`tests/InputScene.tscn` 이 잠근다).

곡 목록의 길이는 오디오 파일이 아니라 **채보의 마지막 히트 시각**이다 —
테스트 채보들이 60초 클릭 트랙을 공유해서 오디오 길이는 오해를 부른다.

새로 클론했을 때: `sh tools/gen_all.sh` 한 번이면 생성 자산 전부 재구성.
