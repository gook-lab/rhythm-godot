# rhythm-godot

A Dance of Fire and Ice(얼불춤) 스타일의 **원버튼 리듬게임**. Godot 4.7 / GDScript.

두 행성이 꺾인 타일 경로를 번갈아 공전한다. 버튼은 스페이스 하나뿐이고,
낙하 노트가 없다 — **타일의 각도가 곧 대기 박자 수**라서 눈이 아니라 귀와 손으로 푸는 게임이다.

설계 배경과 결정 근거: `~/.gstack/projects/rhythm-godot/kyb-ontact-main-design-*.md`

---

## 이 게임의 심장

```
공전 각속도가 박자당 180도로 고정이면, 타일 사이 상대각이 곧 대기 시간이다.

         prev+180 (공전 시작)
              \
               \   sweep
                \ ,-'`
        [pivot]  o------> cur (다음 타일 방향)

    sweep = fposmod(cur - (prev + 180), 360)     # 0 이면 360
    beats = sweep / 180

    직선 (cur==prev)     -> sweep 180 -> 1.0박
    U턴  (cur==prev+180) -> sweep 360 -> 2.0박
    90도 꺾임            -> sweep 270 -> 1.5박
```

따라서 **노트 타임라인이라는 자료구조가 아예 필요 없다.** 각도 배열 하나가
렌더와 타이밍을 동시에 생성한다. 두 개의 진실 소스가 없으므로 둘이 어긋날 수 있는
버그 표면 자체가 사라진다. (대부분의 클론이 여기서 어긋난다.)

### 이 공식은 실측 검증됐다

```bash
python3 tools/verify_formula.py <실제 .adofai 파일들>
```

- ADOFAI 기본 레벨(직선 10타일 @ bpm 100) → **정확히 1.0박 / 600ms 간격**
- 실제 채보 3,155타일 → 최빈값이 정확히 1.0(34%), 모든 값이 1/12 격자, 쓰레기 값 0
- 반증 대조군: `+180` 을 빼면 직선이 **2박**이 되어 즉시 탈락

검증 중 알게 된 것 3가지:

1. **`.adofai` 는 유효한 JSON 이 아니다.** 실제 파일에서 위반 3종 발견 —
   이중 콤마(`"difficulty": 1, ,`), 트레일링 콤마, 섹션 간 콤마 누락.
   `tools/verify_formula.py:load_adofai()` 가 이걸 감안해 읽는다.
2. **CCW/CW 규약은 이 증거로 결정되지 않는다.** 두 변형이 직선·U턴에서 같고
   좌/우 회전에서만 갈린다(1.5 ↔ 0.5). 우리가 채보를 직접 짜므로 무관하지만,
   실제 `.adofai` 를 로드하려면 정해야 한다.
3. **실제 채보는 이 프로젝트가 모델링하는 것보다 훨씬 복잡하다.**
   샘플 채보는 SetSpeed 132개(bpm 128→512)에 Twirl 이 타일의 25%.
   → "직접 짠 채보만 쓴다"는 결정이 옳았다는 증거다.

### 지키는 규칙 7개

**1. 판정은 오디오 클럭 ms 차이로만 한다.** 좌표 겹침도 프레임 카운트도 안 쓴다.

```gdscript
var ms := (get_playback_position() + AudioServer.get_time_since_last_mix()
           - AudioServer.get_output_latency()) * 1000.0
_last_ms = maxf(ms, _last_ms)   # 스레드 지터로 역행할 수 있다(공식 문서 경고)
```

`get_playback_position()` 만 쓰면 오디오 스레드가 다음 청크를 믹싱할 때까지 같은 값을
돌려주므로 클럭이 믹스 버퍼만큼의 계단으로 뚝뚝 뛴다. 그 계단폭이 그대로 판정 잡음이 된다.

**2. `now_ms()` 는 `_input()` 과 `_process()` 각각에서 그 자리에서 부른다. 캐시 금지.**
`_process` 에 캐시한 값을 `_input` 에서 쓰면 최대 1프레임(60fps 에서 16.7ms)이
판정 오차로 그냥 들어간다.

**3. 시간축은 하나뿐이다. `Tween` 을 쓰지 않는다.**
Tween 은 프레임 루프가 굴리는 벽시계라 오디오 클럭과 별개의 두 번째 시간축이 된다.
가장 흔한 증상은 크래시가 아니라 **"행성은 아직 도착 안 했는데 판정은 Perfect"** —
눈과 손이 불일치하는, 진단이 가장 어려운 종류다.
공전각도 카메라 위치도 전부 `now_ms()` 에서 파생시킨다.

같은 이유로 **캘리브레이션 오프셋을 클럭 안에서 빼지 않는다.** 클럭 안에서 빼면
슬라이더를 미는 순간 ① `clamp_hits` 가 올라가고(하드 게이트의 거짓양성)
② `maxf` 가 이전 값을 붙잡아 클럭이 오프셋만큼 얼어붙는다. 오프셋은 판정 시점에 뺀다.

**4. 렌더 커서와 판정 커서는 별개다. 둘 다 `now_ms()` 에서 파생되지만 전진 조건이 다르다.**

| 커서 | 전진 조건 | 쓰는 곳 |
|---|---|---|
| `_idx` (판정) | 입력이 오거나 `hit_time + miss_ms` 경과 | 판정, 판정창 |
| `_vis` (렌더) | `t >= hit_time` — 그냥 시간이 지나면 | 공전각, 카메라, 팝업 위치 |

묶어두면 **행성이 매 타일 `miss_ms` 만큼 얼어붙는다.** 감시자는 늦은 입력을 받아주려고
기한까지 기다려야 하는데, 렌더가 그걸 따라가면 u=1.0 에 붙어서 멈춘다.

실측: 렌더를 판정 커서에 묶으면 전체 프레임의 **25.8%** 가 정지 상태다
(0.5박@120bpm 구간은 250ms 중 110ms = 44%). 분리하면 **0.7%** 로 떨어진다.
`tests/SmokeRunner.gd` 가 이 비율을 재서 8% 를 넘으면 실패시킨다.

**5. 카메라는 두 행성의 '중점'을 따라간다. 타일 사이 직선 lerp 가 아니다.**

직선 lerp 는 행성이 실제로 그리는 호가 아니라 직선을 따라가고, 타일이 바뀔 때마다
진행 방향이 불연속으로 꺾인다(U턴에선 아예 뒤로 간다).

중점은 역할 교체 순간에 **정확히 연속**이다:

```
교체 직전  pivot=P[i-1], 도는 쪽이 P[i] 에 도착  ->  중점 = (P[i-1]+P[i])/2
교체 직후  pivot=P[i],   도는 쪽이 P[i-1]        ->  중점 = (P[i]+P[i-1])/2
```

같은 점이다. 위치 점프가 원천적으로 사라진다.

| 프레임당 카메라 이동 | 직선 lerp | 중점 |
|---|---|---|
| 중앙값 | 2.13 px | 2.00 px |
| **p99** | **25.11 px** | **3.01 px** |
| 최대 | 29.35 px | 7.41 px |

흔들림은 `position` 이 아니라 `offset` 으로 준다 — `position` 에 실으면
`position_smoothing` 이 흔들림을 뭉개서 '흔들림'이 아니라 '느린 표류'가 된다.

**6. 채보에는 카운트인이 있어야 한다 (기본 4박).**

음악적으로도 필요하지만 기술적으로도 필요하다. `AudioClock` 워밍업(100ms) 동안
렌더가 멈춰 있는데, 첫 타일이 0ms 에 있으면 warm 되는 순간 그만큼을 한 번에
건너뛰어 카메라가 32px 튄다. `tools/make_charts.py:LEAD_IN_BEATS`.

**7. 인덱스는 `angles[i-2]`(들어온 방향)와 `angles[i-1]`(나갈 방향)이다. `angles[i]` 가 아니다.**

타일 `i` 로 가는 공전은 축이 타일 `i-1` 이고, 도는 행성이 타일 `i-2` 에서 출발해
타일 `i` 에 착지한다. 그러니 스윕을 정하는 건 `angles[i-2]` 와 `angles[i-1]` 이다.
`angles[i]` 는 타일 `i` 에서 그 다음으로 나갈 방향이라 한 칸 미래다.

첫 구현이 여기서 한 칸 밀려 있었다. **직선 구간에선 착지 오차가 정확히 0 이라
전혀 안 보이고**, 꺾이는 데서만 드러난다:

| 경로 | 밀렸을 때 착지 오차 | 고친 뒤 |
|---|---|---|
| 직선 | 0.00 px | 0.00 px |
| 90도 계단 | 135.76 px | 0.00 px |
| 사각형(90도 4연속) | 135.76 px | 0.00 px |
| U턴 | 192.00 px | 0.00 px |

타일 간격이 96px 이니 최대 두 칸을 벗어난 채 내렸다가 튄 것이다.
`tests/run_tests.gd:t_landing()` 이 여섯 가지 경로 모양에 대해 좌표로 잠근다.
`tools/make_charts.py` 도 채보를 만들 때마다 같은 불변식을 잰다.

## 실행

```bash
# 곡(메트로놈 클릭) 생성 — BPM 이 샘플 단위로 정확해야 한다
python3 tools/make_click.py 120 60

# 채보 생성 — 각도를 손으로 안 쓴다. 박자 패턴에서 역산한다
python3 tools/make_charts.py

# 단위 테스트 (의존성 0) — 85종
godot --headless --script res://tests/run_tests.gd

# 통합 스모크 (전곡 자동 완주, 감시자/곡종료/클럭 역행 검증)
godot --headless --audio-driver CoreAudio res://tests/SmokeScene.tscn

# 오디오 클럭 실측 (드리프트·지터·3항vs1항)
godot --headless --audio-driver CoreAudio --script res://tests/probe_clock.gd

# 실행
godot -e     # 에디터
godot        # 바로 실행
```

**조작:** `스페이스` 판정 · `R` 재시작

### 곡을 왜 만들어 쓰나

음악은 BPM 이 정확히 알려져 있지 않거나 변속이 있거나 그루브가 있다. 판정이 어긋났을 때
원인이 내 코드인지 곡인지 구분이 안 된다. 클릭은 샘플 단위로 정확하다 —
실측 결과 간격 오차 최대 0.042ms, 60초 누적 드리프트 +0.08ms.

WAV 를 쓰는 이유: 손실 압축은 어택 트랜지언트를 뭉갠다. 디코더 지연 편차도 없다.
용량이 크므로 gitignore 하고 생성기만 커밋한다.

### 계측 결과 (2026-08-07, Apple Silicon / macOS)

```
godot --headless --audio-driver CoreAudio --script res://tests/probe_clock.gd
```

| 항목 | Dummy (기본 헤드리스) | **CoreAudio (실제)** |
|---|---|---|
| 드리프트 (속도 오차) | −4.03 % | **−0.02 %** |
| 지터 (추세 제거 후 표준편차) | 7.86 ms | **0.78 ms** |
| 역행 횟수 (3초) | 7 | **0** |

**오디오 클럭이 먹는 몫은 0.78ms다.** 성공기준 3의 예산이 15ms이므로
나머지 14ms 이상이 입력 경로와 사람 손 몫으로 남는다.
이 프로젝트가 가장 걱정하던 리스크(오디오 클럭이 손맛을 죽인다)는 해소됐다.

**헤드리스 기본값(Dummy)의 −4% 드리프트에 주의.** 드리프트는 캘리브레이션으로
못 잡는다(시간이 갈수록 벌어지므로). 자동 타이밍 측정을 돌릴 거면 반드시
`--audio-driver CoreAudio` 를 붙여야 한다. 붙이면 CI 에서도 잴 수 있다.

#### 3항 vs 1항 — 크로스모델 논쟁 종결

| 공식 | 지터 |
|---|---|
| **3항** `pos + since_mix - latency` | **0.78 ms** |
| 1항 `pos` 만 | 3.44 ms |

독립 리뷰어가 "3항은 과잉이니 `get_playback_position()` 만으로 시작하라"고 했고,
반박은 "그 항은 변덕에 대한 보험이 아니라 상시 존재하는 계단 현상을 메우는 항"이었다.
**실측 결과 3항이 지터를 2.66ms 줄인다** — 전체 15ms 예산의 18%다. 조기 최적화가 아니다.

#### 아직 안 잰 것

| 설정 | 표준편차 |
|---|---|
| `agile_event_flushing` OFF (기본) / ON | ? ms |
| `vsync_mode` ON / OFF | ? ms |
| `output_latency` 15ms / 낮춤 | ? ms |

입력 경로 설정은 **사람이 실제로 키를 쳐야** 잴 수 있어서 프로브로는 안 된다.
게임을 띄워 놓고 디버그 오버레이의 표준편차를 보면서 켜고 꺼야 한다.

### 성공 기준

1. 30초 이상 완주 + **연속 3회 재시작**해도 판정 동일 (`_last_ms` 리셋 검증)
2. 오프셋 슬라이더 ±150ms, 다음 판정부터 즉시 반영
3. **판정 오차 표준편차 < 15ms** — 같은 구간 10회 반복, 모든 `delta_i` 를 한 표본으로
   - 미달 시: 즉시 실패로 보지 말고 오디오 백엔드·버퍼·`output_latency` 실측값부터 로그.
     백엔드를 바꿔도 안 줄면 그건 코드 결함이 아니라 기계의 바닥이다.
     **코드 결함과 기계 바닥을 구분하는 게 목적이지 15라는 숫자가 목적이 아니다.**
4. **클럭 역행의 *크기*가 한 믹스 청크(~6ms)를 넘지 않을 것.** 횟수가 아니다.
   - 실측: 20초 재생에 역행 20회, 최대 5.7ms. **0 이 아닌 게 정상이다.**
     `get_playback_position()` 과 `get_time_since_last_mix()` 가 서로 독립적으로
     갱신돼서, 믹싱 직후에 샘플링하면 옛 `pos` 에 리셋된 `since_mix` 가 붙는다.
     구조적으로 일어나는 일이고 단조 클램프가 바로 그걸 막으라고 있다.
   - `get_output_latency()` 를 시작 시점에 고정해봐도 크기가 그대로였다 —
     latency 지터가 원인이 아니다.
   - **슬라이더를 아무리 밀어도 역행이 늘면 안 된다** — 늘면 오프셋이 아직
     `now_ms()` 안에 남아 있다는 신호다.
5. 판정 피드백이 입력 후 33ms 이내

## 판정과 점수

### 7등급 (얼불춤 체계)

```
TooEarly · VeryEarly · EarlyPerfect · Perfect · LatePerfect · VeryLate · TooLate
```

Perfect 가 3종(E/일반/L)이고 **일반 Perfect 만 정확도 만점**이다. 이게 있어야
"다 맞혔지만 살짝씩 어긋난" 플레이와 "정확한" 플레이가 구분되고, 손맛을
개선했는지 알 수 있다. 랭크는 `P / SS / S / A / B / C / D / F` —
P 는 전부 일반 Perfect 일 때만 나온다.

### 판정창은 BPM 에 따라 좁아진다

고정 ±110ms 로 두면 **인접 타일 간격이 220ms 밑으로 내려가는 순간 판정창이 겹쳐서
한 번 누른 입력이 두 타일 모두에 유효해진다.**

| 박자 | bpm | 간격 | 고정창(±110) 여유 |
|---|---|---|---|
| 0.5박 | 120 | 250ms | +30ms (아슬아슬) |
| 0.5박 | 140 | 214ms | **−6ms 겹침** |
| 1/6박 | 340 | 29ms | **−191ms 붕괴** |

그래서 판정 사다리 전체를 **이웃 타일까지 거리의 절반**으로 캡한다
(`Judge.set_gaps()`). 겹침이 구조적으로 불가능해지고, 등급 간 비율은 보존된다.
얼불춤도 같은 이유로 "빠를수록 엄격"하게 만든다.

`tests/run_tests.gd:t_judge_windows()` 가 250·214·125·29·8ms 간격에서
창 폭이 간격을 절대 못 넘는지 잠근다.

### HUD

- **TimingScale 바** — 가운데가 정확, 왼쪽이 빠름. 최근 40개 입력이 눈금으로 찍히고
  파란 삼각형이 평균이다. **연출이자 계측 도구다**: 눈금이 한쪽으로 쏠렸으면
  오프셋 문제(슬라이더로 고쳐짐), 가운데를 중심으로 넓게 퍼졌으면 산포 문제(안 고쳐짐).
  판정창이 좁아지면 바 축척도 같이 확대돼서 눈금이 뭉치지 않는다.
- **체감 BPM** = 타일 BPM ÷ 현재 홉 박자. 1/6박 홉을 340bpm 으로 밟으면 2040 이다.
  판정창이 왜 좁아져야 하는지를 화면에서 바로 보여주는 숫자다.
- 랭크·정확도·콤보 · 음악 시간 · 역행 횟수와 최대 크기 · output_latency · fps

### 연출

네온 글로우(HDR 2D + `WorldEnvironment` glow — 색을 1.0 넘게 주면 그 부분만 블룸),
판정 등급별 행성 색 플래시(2프레임), 미스 시 화면 흔들림.
**흔들림만 프레임 시간으로 감쇠한다** — 오디오 클럭과 무관한 순수 연출이라서다.
그 외 모든 시각 요소(공전각·카메라)는 여전히 `now_ms()` 에서 파생된다.

## 테스트 제약

**`--script` 모드에선 autoload 가 등록되지 않는다.** `AudioClock` 식별자를 못 찾아서
`Main.gd` 자체가 컴파일에 실패한다. 그래서 `Main` 을 태우는 통합 테스트는
`--script` 가 아니라 **씬**(`tests/SmokeScene.tscn`)으로 만들어 정상 실행 경로에 태운다.
순수 함수만 보는 `run_tests.gd` 는 `class_name` 글로벌만 쓰므로 `--script` 로 된다.

### 잔상 트레일

두 행성이 지나간 자리를 22프레임 남긴다. 오래된 쪽이 얇고 투명해진다
(`PlanetPair._draw_trail`). 굵기가 선분마다 달라야 해서 `draw_polyline` 대신
개별 `draw_line` 으로 그린다 — 폴리라인은 굵기가 하나뿐이다.

트레일은 **'기록'이지 '구동'이 아니다.** 매 프레임 위치를 남기기만 하고
아무것도 움직이지 않으므로 규칙 3(시간축 하나)을 깨지 않는다.
축 행성은 안 움직이므로 같은 자리가 쌓이지 않도록 1px 미만 이동은 버린다.
